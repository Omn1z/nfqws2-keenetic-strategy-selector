# Нативная панель для Keenetic и OpenWrt

Ветка `rust` содержит самостоятельный HTTP-сервер `nfqws2-strategy`. На роутере он читает каталог данных существующей панели. Состояние переноса проверяется по HTTP-контракту, форматам файлов и поведению служб. Исходная Go-реализация пока нужна для рабочих установок с полным набором функций и для сравнительных тестов.

## Состав

| Область | Реализация в Rust |
| --- | --- |
| Панель | HTTP, авторизация по данным роутера, cookies, журналы и общие настройки. Смена HTTP-порта и перезапуск служб панели с перечитыванием данных. Полный и компактный варианты интерфейса. |
| Данные | Атомарная запись JSON и межпроцессная блокировка. Восстановление защищённых документов по двум контрольным снимкам Go. Импорт и экспорт резервных копий формата SLBAK1. |
| Мониторинг | CPU, память, swap, процессы, температуры, занятое место, трафик WAN, очередь NFQUEUE, соединения и устройства. Большая таблица conntrack передаётся порциями. По таблице IPv6-соседей панель связывает IPv4 и IPv6 одного LAN-клиента с его MAC. Учитываются и публичные IPv6-адреса в делегированной сети. |
| DNS | UDP, TCP и DoH с проверкой TLS, пулы по доменам, кеш и планировщик. В режиме «только VPN» DoH и разрешение имени его сервера используют выбранный работающий интерфейс AWG. При потере туннеля запрос завершается ошибкой. Для явно настроенных доменов Shadow действует отдельный маршрут к DNS провайдера. Shadow проверяет активный WAN по DHCP ACK, сессии PPPoE IPCP или netifd. Настройки DNS OpenWrt восстанавливаются через UCI. Список AdGuard скачивается при включении, затем проверяется раз в сутки. Для разрешения имени издателя и загрузки используется один маршрут с приоритетом доступных AWG. Сбой обновления сохраняет предыдущий снимок. |
| Роутер и NFQWS2 | Обнаружение системных путей, ручное применение аргументов и сервисных профилей, управление vendor init, проброс портов, исключения NFQUEUE, проверка и обновление пакета opkg/apk. Смена порта панели сохраняет открытые HTTP-соединения. |
| Сеть | SOCKS5 CONNECT с аутентификацией, MTProto через WSS и TCP, входящий PROXY v1, пулы соединений по дата-центрам Telegram. Поддерживаются Worker, загрузка штатного каталога CF через HTTPS и HTTP/2 для медиа. Для штатных узлов DC1/3/5 доступен повтор через выбранный AWG-интерфейс с действующим маршрутом. Штатная изоляция Wi-Fi клиентов Keenetic проверяет ревизию конфигурации и результат изменения. |
| Профили AWG | Импорт и экспорт, редактирование, установка внешнего движка с проверкой SHA‑256 и ELF, локальные клиенты, резервные endpoint и standby для прокси. Обычная регистрация WARP требует принятия условий Cloudflare. Проверка туннеля использует HTTPS и счётчики handshake UAPI. |
| Данные стратегий | Ручные стратегии, SNI, списки, хранилище блобов, корзина и генерация TLS ClientHello. Экспорт ZIP и снимки. При импорте сервисные профили компилируются для путей текущего роутера. Предпросмотр проверяет ревизию и учитывает пользовательские списки. |
| Маршрутизация AWG | IPv4 и IPv6 для адресов, CIDR, точных имён и масок доменов. Первое совпавшее правило выбирает туннель или прямой выход с учётом сети источника. Политика поддерживает до 64 физических туннелей. Предел селекторов зависит от типа политики и приведён ниже. При отказе панель проверяет ключ резервного пира и покрытие назначения его AllowedIPs. При полном отказе действует выбранный прямой выход или блокировка. Доступны пробное применение на 90 секунд, подтверждение, откат и восстановление после перезагрузки. Объекты ядра сверяются с журналом владения. |
| Диагностика | HTTPS-прогоны через текущую конфигурацию, история, отмена и смена числа потоков. BlockCheck, пассивная трассировка устройств, PCAP, трассировка DNS и заголовков AWG, потоковый замер скорости WAN и AWG. Импорт GeoSite/GeoIP и текстовых списков. |
| CLI | `serve`, `version`, `config`, восстановление OpenWrt DNS, `checkupdate`, `update` и HTTPS-самопроверка без запуска сервера. `selftest -s ИНДЕКС ИМЯ` проверяет одну встроенную стратегию, по умолчанию с индексом 0. `selftest --current ИМЯ` проверяет текущее соединение. Для компактной сборки нужны модуль прогонов и, при выборе стратегии, модуль стратегий. |
| Инструменты разработчика | Отдельный клиент router-ssh вызывает системный OpenSSH. Генератор поправок для внешнего движка AWG перенесён на Rust. |

Команда `python3 scripts/rust-route-coverage.py --check --missing` сравнивает методы и пути HTTP. В Rust совпадают все 189 из 189 регистраций Go, включая `POST /api/nfqws2/automation/pick-now`. Проверка больше не допускает исключений для отсутствующих маршрутов. Совпадение регистраций не означает полного совпадения поведения всех служб; ограничения перечислены ниже.

Очередь DoH поддерживает до 126 различных AWG-маршрутов и системный маршрут, если он разрешён политикой. Лимит 32 действует на одновременные запросы. При выключенной адаптации порядок совпадает с Go. Сначала проверяются разрешённые маршруты основного провайдера, затем маршруты следующих провайдеров.

Если у одного DoH-сервера несколько IP-адресов, попытки используют общий таймаут на выбранном маршруте. Ошибка соединения или некорректный ответ переключает запрос на следующий адрес. Последний адрес с действительным ответом получает приоритет для следующего запроса к тому же серверу через тот же маршрут.

При восстановлении повреждённых настроек DNS из проверенной копии панель показывает `config_warning`. Если основной файл и все копии повреждены, панель возвращает `config_error` и оставляет редактирование недоступным до явного восстановления. Выключенное состояние, правила и отключённые методы сохраняются при автоматическом восстановлении. Выключенный DNS продолжает показывать адрес и порт для настройки роутера. На OpenWrt запуск с выключенным DNS возвращает прежние параметры dnsmasq из журнала панели, если они по-прежнему принадлежат панели. При сохранении старой формы DNS поля со значением `null` сохраняют прежние настройки. Явные `false` и пустые списки применяются. Правила с отсутствующим или пустым переключателем `enabled` загружаются выключенными. При перестановке старых правил без сохранённого ID резервные DNS-серверы переносятся по идентификаторам, которые показывает панель. У новой строки без настроенных серверов пул остаётся пустым.

При пробросе портов буквальные имена WAN из Go сохраняются. Для маски `ISP_INTERFACE`, например `ppp+`, панель выбирает совпадающий интерфейс с активным маршрутом IPv4 по умолчанию и подтверждённой ролью WAN. Хук перепроверяет устройство при очередном применении правил firewall. Без подтверждённого WAN управляемые правила проброса остаются пустыми.

Замер скорости AWG использует отдельные TCP-сокеты IPv4 для туннеля и WAN. До соединения панель привязывает сокет к интерфейсу и задаёт метку `0x20000000`, как Go. Так правило полной маршрутизации AWG не перехватывает пробу WAN. HTTPS проверяет сертификат. Результат и ход замера передаются прежним потоком NDJSON.

Изоляция Wi-Fi использует тот же хеш конфигурации, что Go. Запрос с ревизией, полученной до обновления, проходит проверку при неизменённом сегменте. Список клиентов объединяет записи ассоциаций и DHCP по нормализованным MAC, включая формат с точками.

### Прогоны стратегий

С установленным пакетом прогонов панель предлагает измерить текущую конфигурацию или запустить «Прогоны стратегий». Обычный `POST /api/runs` принимает сохранённый список или ручные цели, выбранные стратегии, варианты из blob-файлов и сохранённые DNS-профили. Автоподбор внутри прогона использует встроенные TLS-кандидаты. DNS-профили DoH и DoT проверяют TLS и передают в HTTPS-пробу подтверждённый адрес. Загрузки через выбранную стратегию проверяются в изолированной очереди. Победители записываются в «Списки» по завершении прогона.

### Автоматический подбор стратегии

Ручной «Подобрать сейчас» запускает самостоятельный Rust-исполнитель и возвращает HTTP 202 со статусом автоматики. Повторный запрос во время подбора, занятый диагностический исполнитель и ручное выключение NFQWS2 возвращают HTTP 409. В компактной установке нужен пакет прогонов `nfqws2-strategy-runs`.

Автоподбор проверяет пять доменов из Go: `youtube.com`, `googlevideo.com`, `instagram.com`, `x.com` и `openai.com`. Сначала измеряется доступность без обхода, затем на заблокированных доменах сравниваются 43 автоматических TLS-кандидата, установленные и пользовательские HTTPS-стратегии, включая варианты сохранённых SNI. Совпадающие аргументы удаляются. Тестовые процессы используют собственные очереди NFQUEUE и диапазоны исходящих портов. Успешный запрос учитывается только при прохождении пакетов через тестовую очередь. Для этой проверки на Linux нужны `curl`, NFQWS2 и совместимые `iptables`; одна лишь маршрутизация fw4 через nftables не обеспечивает этот режим.

Побеждает стратегия, которая прошла все проверяемые домены и получила наибольший коэффициент скорости с учётом времени первого байта. Результат доступен в обычной истории прогонов. Перед записью панель повторно проверяет TLS/TCP 443, ручное выключение NFQWS2 и переключатели фонового подбора. Исходная конфигурация сохраняется в `nfqws2.conf.n2s.bak`, затем обновляется `NFQWS_ARGS` и перезапускается служба. Если перезапуск не удался, новая конфигурация и резервная копия остаются для диагностики, а ошибка сохраняется отдельно от последнего успешного подбора. Если без обхода доступны все домены, стратегия не применяется.

Фоновые режимы по умолчанию выключены. `auto_pick` разрешает подбор при первом запуске с пустым `NFQWS_ARGS`, а существующая стратегия сохраняется. Периодический подбор дополнительно требует `periodic_scan`, истечения `interval_h` и исправного AWG-соединения. Текущий цикл автоматики использует один замер AWG для решения о запуске сервиса и подбора. Ручной запуск работает независимо от этих двух переключателей. Подбор ограничен восемью минутами. Отмена и остановка панели ожидают завершения исполнителя и очистки тестовых правил.

Первое сохранение состояния автоматики записывает режим `off` и интервал 24 часа, если этих значений ещё нет. После первой ручной остановки NFQWS2 на чистой установке Go при возврате читает сохранённый флаг выключения из того же файла.

Перед запуском, пробой восстановления и переключением endpoint AWG панель обновляет пары UDP-адреса и порта в действующей цепочке NFQUEUE, если установлен штатный обработчик. Она сохраняет уже применённые списки и наборы ipset. Если NFQWS2 вручную выключен, пары сохраняются для следующего запуска. При конфликте с другим изменением настроек попытка откладывается. Ошибка при обновлении одного семейства запускает восстановление ранее проверенных правил.

Правка работающего импортированного профиля AWG и удаление используемого резервного endpoint сохраняются до попытки запуска обновлённого туннеля. Если применение временно недоступно, панель повторяет попытку по сохранённой записи. Перед остановкой прежнего процесса проверяется его принадлежность профилю. Ошибка применения сохранённого списка резервов возвращается в поле `warning` ответа API.

При выключенной маршрутизации и остановленных зависимых туннелях в диалоге удаления подключения можно перенести его зоны, резервы и ссылки на внешний туннель на выбранное подключение. Перед сохранением панель проверяет зависимости и циклы. Она сохраняет порядок зон, номера интерфейсов и параметры действующей конфигурации при ожидающем развёртывании.

Перенос неактивного подключения также доступен, когда другой импортированный туннель под управлением Rust обслуживает подтверждённый маршрут по одному IPv4-префиксу. Панель сверяет неизменность правила и маршрута, затем обновляет подтверждённую ревизию. Прерванную запись ревизии можно восстановить без перезапуска действующего туннеля.

Для двух уже работающих прямых импортированных туннелей можно перенести один подтверждённый IPv4-префикс с удалением исходного профиля. Kill Switch сохраняется при смене маршрута и откате. Исходный процесс останавливается после проверки маршрута через замену и сохранения переноса. Если запись прервана, панель сверяет журнал и возобновляет откат или завершает остановку подтверждённого владельца.

Если выбранный прямой резерв остановлен, панель запускает его временно и ждёт свежего рукопожатия. Исходный туннель обслуживает маршрут до подтверждения замены. При таймауте или сбое сохраняются прежний профиль и маршрут. После прерванной попытки панель сверяет запись владельца временного процесса перед очисткой.

Для импортированного туннеля под управлением Rust с подтверждённой статической политикой можно отдельно изменить MTU или основной UDP-адрес. В явных зонах панель проверяет новый WAN-маршрут и сверяет адрес с действующим и подтверждённым планами, включая клиентские, резервные и DNS-маршруты. Прямой и вложенный туннели допускают смену между IPv4 и IPv6 при прежних внутренних адресах и `AllowedIPs`. Для вложенного туннеля панель дополнительно проверяет выбранный внешний пир, путь через него и фактический MTU с учётом нового семейства транспорта. Перед перезапуском сохраняются действующий Kill Switch, выученные DNS-адреса и пути других интерфейсов. После подтверждения пира, фактического MTU, адреса процесса и покрытия маршрутов панель восстанавливает пути и рассчитывает MSS в той же ревизии политики. При фактическом MTU ниже 1280 IPv6 использует подтверждённый резерв или блокируется. Для одновременной правки адреса с другими параметрами соединения требуется предварительно снять статическую политику.

В подтверждённом прямом полном туннеле Rust без зон, ограничений по источнику и резервных туннелей можно заменить числовой IP на другой адрес того же семейства. Перед остановкой пира панель проверяет WAN с меткой транспортного сокета, устанавливает исключение для нового IP и повторно проверяет обычный маршрут. Оба адреса сохраняются до подтверждения нового пира или отката. После подтверждения лишнее исключение удаляется, если адрес больше не используется другим подключением или резервом.

Если до смены IP в полном туннеле действовал IPv4 и была установлена блокировка IPv6, новая версия туннеля сначала подтверждает IPv4. Дальнейший доступ IPv6 определяет штатная проверка маршрута.

Смена числового IPv4 также доступна в унаследованной одиночной полной политике Go, когда процесс AWG уже управляется Rust, а WAN блокирует пересылку IPv6 правилом `ForwardReject`. При смене адреса панель сохраняет это правило и проверяет, что путь к новому endpoint использует тот же WAN. После подтверждения нового IPv4-соединения возобновляется штатная проверка доступности IPv6.

Если до смены адреса работали оба семейства, после подтверждения нового IPv4 панель открывает только IPv6-маршрут для пробы, привязанной к интерфейсу AWG. Успешная свежая проба возвращает пересылку IPv6 через туннель. Если проба по подтверждённому пути не прошла, панель завершает смену адреса с действующим IPv4 и прежней защитой от выхода IPv6 через WAN. Обычная проверка туннеля сможет вернуть IPv6 позже.

В прямом туннеле с явными зонами endpoint можно заменить числовым адресом или именем с UDP-портом. Панель разрешает новое имя до блокировки изменений маршрутов, проверяет полученные адреса и выбирает первый IPv4 для запуска. Имя остаётся в профиле, а журнал хранит DNS-ответы и точный выбор для повторного запуска. При смене сохранённого имени журнал записывает адрес подтверждённого работающего пира. Откат восстанавливает старое имя и сохранённый адрес даже после смены DNS-ответа. Если оба имени указывают на один UDP-адрес, панель сверяет отпечаток новой конфигурации. Обычный запуск по имени также выбирает первый IPv4 из результатов системного резолвера. Числовой IPv6 принимается напрямую.

Если новый основной адрес ещё ожидает подтверждения, через ту же форму можно сохранить точный прежний endpoint. Панель возвращает пути после подтверждения прежнего адреса действующим процессом. При обрыве операции отмена продолжится по той же записи перехода, включая проверку исключений NFQUEUE и сохранение резервов.

Если при редактировании профиля с DNS-именем работал числовой резерв, панель отдельно сохраняет его фактический IP и UDP-порт. При совпадающих портах она предварительно проверяет свежие DNS-ответы, чтобы отличить резерв от основного адреса. Отмена восстанавливает прежнее имя и подтверждённый резерв без повторного DNS-запроса. Резерв должен оставаться в настройках профиля и быть доступен через WAN.

Для прямого AWG в раздельных зонах, если новый основной адрес доступен по WAN, но пир не отвечает, клиент после штатной проверки соединения пробует сохранённые резервные UDP-адреса. Перед перезапуском панель проверяет маршрут к выбранному резерву и сохраняет точный адрес и порт в журнале. Маршруты возвращаются после свежего рукопожатия процесса с новой конфигурацией. Работающий резерв остаётся выбранным, пока соединение исправно.

Если WAN до нового основного адреса отсутствует уже при сохранении, панель может запустить новую конфигурацию на подтверждённом резерве. Старый процесс продолжает работу до записи выбранного UDP-адреса в журнал и парковки маршрутов. После обрыва панель проверяет сохранённый выбор перед повтором. Ошибки чтения маршрута требуют повторной проверки.

Если ядро подтверждает отсутствие WAN у всех числовых адресов прямого профиля, панель сохраняет правку и ждёт доступного пути. Прежний процесс обслуживает подтверждённые маршруты и DNS, пока его адрес, владелец и WAN остаются подтверждёнными. После полной перезагрузки защитные правила сохраняются до подтверждения нового соединения.

Если основной адрес теряет WAN после запуска нового клиента, подтверждённый прямой резерв продолжает работу. При обновлении правил и DNS панель сверяет запись владельца текущего процесса и WAN-маршрут резерва. Основной IP сохраняется в проверке пересечений с политикой. Если этот IP используется другим соединением или резервом, его WAN-маршрут также проверяется.

В постоянном двойном туннеле раздельные зоны могут использовать числовой основной endpoint, доступный через выбранный внешний AWG. Для такого адреса панель сверяет владельца процесса, точную пару IP и UDP-порта, метку сокета и маршрут по этой метке. Проверка повторяется при восстановлении правил и обновлении DNS-зон. При потере подтверждения постоянный профиль ждёт выбранный внешний пир, а его зоны сохраняют действие настроенного Kill Switch. Для IP, используемых другими профилями или резервными адресами, применяется обычная проверка WAN.

Импорт `vpn://` читает zlib-профили Go с нулевым или неточным полем длины qCompress. Распакованный документ ограничен 4 МиБ. Адреса из полей DNS подставляются только в строку DNS, поэтому профиль с одним адресом работает и при пустом втором поле. При импорте `.conf` принимаются пробелы вокруг имён секций, а параметры wg-quick `Table`, `SaveConfig` и `FwMark` пропускаются. Правила маршрутизации и состояние запуска задаёт панель.

Для клиентов AWG под управлением Rust панель показывает время последнего handshake и последнего подтверждённого входящего трафика. При устойчивом исходящем трафике без ответа проверка пира по умолчанию начинается примерно через 20 секунд. Если ответа по-прежнему нет, ещё через `handshake_timeout_seconds` (по умолчанию 20 секунд) начинается восстановление. Возможна дополнительная задержка до следующего опроса. При полном простое проверка ждёт истечения срока ключа. Рост RX или новое рукопожатие отменяет восстановление.

При автоматическом переподключении прямого профиля с DNS-именем и подтверждёнными явными зонами панель запрашивает A-записи вне блокировок маршрутов. Перед остановкой прежнего процесса она сверяет профиль, ревизию маршрутов, состояние пира и фактический WAN для первого полученного IPv4. Ответ отбрасывается, если за время запроса пир восстановился или изменилась конфигурация. Сохранённые адреса незавершённой правки по-прежнему берутся из журнала.

Если свежий запрос не дал адреса и последняя операция DNS-маршрутизации завершилась ошибкой, панель может взять ранее принятый ответ для того же профиля. Срок в 20 минут отсчитывается от последнего свежего ответа, прошедшего проверку. Перед запуском панель повторно проверяет WAN, маршруты и состояние DNS-политики.

При штатном обновлении с Go работающий прямой AWG-туннель сохраняет процесс и соединение. До остановки Go установщик сверяет соединение с ключами профиля и записывает идентификаторы процесса, сокета и сетевого интерфейса. После проверки маршрутизации Rust использует эту запись для наблюдения. Если проверочный keepalive подтвердил отказ, watchdog ещё раз сверяет владельца, штатно останавливает этот процесс и запускает движок по сохранённому профилю. Для остальных занятых интерфейсов доступно наблюдение. Остановленные пользователем профили остаются выключенными. Холодный резерв ждёт отказа основного соединения.

Для унаследованного прямого подключения с подтверждёнными явными зонами можно изменить числовой IP или UDP-порт основного endpoint в пределах одного семейства адресов. Панель проверяет запись установщика, действующее соединение и WAN для выбранного адреса. Маршруты остаются защищёнными во время смены процесса и открываются после рукопожатия на новом endpoint. Для нового соединения панель запускает тот же официальный движок `amneziawg-go`.

В таком подключении можно отдельно изменить MTU при сохранении числового endpoint. Панель сверяет прежний процесс и фактический MTU, затем подтверждает новый процесс с тем же UDP-адресом и новым MTU перед восстановлением маршрутов.

Адрес и MTU унаследованного прямого подключения также можно сохранить одним запросом. Для адресов одного семейства подтверждается вся новая пара. При отмене восстанавливаются прежний endpoint и исходная форма поля MTU.

В подтверждённых явных зонах унаследованный прямой профиль с именем endpoint можно перевести на другой числовой UDP-адрес того же семейства. Панель записывает исходное имя и подтверждённый UDP-адрес прежнего процесса. При отмене профиль получает исходное имя, а запуск использует записанный адрес без повторного DNS-запроса. Маршруты возвращаются после проверки владельца, WAN и точного UDP-адреса.

При замене числового IPv4 endpoint таким именем панель заново получает A- и AAAA-записи, проверяет полученные адреса и сохраняет их на время операции. Для подключения используется первый A-адрес. Откат возвращает прежнюю числовую запись без обращения к DNS.

Имя и числовая запись могут указывать на один UDP-адрес. В этом случае исключение для транспорта сохраняется в одном экземпляре, а перед восстановлением маршрутов панель проверяет отпечаток конфигурации новой записи и владельца процесса.

Пока отдельная правка MTU ожидает подтверждения, можно повторно сохранить прежнее значение. Для правок с записью исходной формы панель восстанавливает само поле, включая его отсутствие, `0` или `null`. Маршруты возвращаются после подтверждения прежнего фактического MTU на том же endpoint.

Такой же откат поддерживается для прямого импортированного туннеля под управлением Rust в подтверждённых явных зонах, если во время первоначальной правки панель подтвердила фактический основной UDP-адрес. При работающем соединении с прежним MTU его можно использовать после проверки владельца и WAN.

Если в таком туннеле работает настроенный числовой резерв, смена или откат MTU сохраняет его точный UDP-адрес. Это действует и при потере WAN-маршрута к основному адресу. Пока правка ожидает подтверждения, маршруты через туннель возвращаются только после проверки владельца процесса, адреса резерва и фактического MTU. После завершения операции настройки основного адреса сохраняются.

Одиночный полный туннель под управлением Rust поддерживает смену и немедленную отмену MTU на прежнем числовом основном UDP-адресе. Исключение для этого адреса остаётся в таблице. Если IPv6 был заблокирован до правки, его доступность повторно проверяет штатное обновление уже после завершения операции.

Для постоянного двойного туннеля под управлением Rust в подтверждённых явных зонах MTU можно вернуть до завершения правки, если основной числовой endpoint внутреннего туннеля и выбранный внешний туннель сохранились. Панель восстанавливает исходную форму поля MTU и проверяет отпечаток конфигурации процесса и помеченный маршрут через внешний туннель. Проверка действует и когда ограничение внешнего туннеля даёт одинаковый фактический MTU до и после правки.

Если постоянный двойной туннель работает на подтверждённом числовом резерве, смена и откат MTU сохраняют точный UDP-адрес этого резерва и исходный основной адрес в конфигурации. Панель проверяет помеченный внешний путь и отдельный WAN-маршрут к резерву, в том числе когда основной адрес и резерв отличаются только портом. После перезапуска панели действующее соединение с резервом можно подхватить. Новый запуск туннеля без незавершённой правки начинает с основного адреса.

Для подтверждённого числового основного адреса постоянного двойного туннеля можно за одно сохранение изменить UDP-порт и MTU, оставив IP и внешний туннель прежними. При отмене восстанавливаются порт и исходная форма поля MTU. Даже при одинаковом фактическом ограничении MTU маршруты ожидают точного UDP-адреса и подтверждения владения новым процессом.

Так же можно изменить числовой IP, в том числе перейти между IPv4 и IPv6. Перед сохранением панель проверяет оба адреса на пересечение с подтверждёнными маршрутами, а новый адрес сверяет с `AllowedIPs` внешнего пира и пригодным исходным адресом нового семейства. После смены маршруты возвращаются через тот же подтверждённый внешний туннель. При фактическом MTU ниже 1280 IPv6 остаётся закрытым. Отмена восстанавливает прежний UDP-адрес и MTU.

Для прямого импортированного профиля под управлением Rust один запрос может сохранить числовой endpoint и MTU вместе. В подтверждённых явных зонах можно перейти между IPv4 и IPv6. Для выбранного адреса панель проверяет совпадение обычного и помеченного WAN-пути. При отмене достаточно исправного WAN прежнего адреса. В одиночном полном туннеле с действующим IPv4 поддерживается смена адресов одного семейства. Если в полном режиме IPv6 уже был заблокирован, подтверждение новой пары возвращает IPv4. IPv6 откроется после отдельной штатной проверки. Прежний фактический и новый MTU должны быть в диапазоне 1280–1500. После подтверждения маршрутов панель обновляет MSS. При точном откате старого профиля восстанавливается и исходный вид поля MTU, в том числе отсутствие поля, `0` или `null`.

Обычные HTTPS-прогоны проверяют доступность через текущую конфигурацию. Автоподбор запускает отдельную матрицу стратегий. Rust читает режимы вложенного туннеля `automatic`, `last_resort`, `preferred` и `permanent` из конфигурации Go. Для постоянного режима запуск внутреннего туннеля ждёт готовности внешнего. Проверка вложенного соединения учитывает handshake, маршрут транспорта и ответ HTTPS через внутренний интерфейс. В зональной политике `AWG2_MULTI` Go завершает прежний обработчик TLS ClientHello при применении правил. Rust сохраняет такое поведение и обучает маршруты по DNS. Движком туннеля на роутере остаётся официальный `amneziawg-go`. Для изменения конфигурации на VPS администратор отдельно запускает развёртывание из панели. Обработка NFQUEUE использует внешний движок NFQWS2.

Fast DNS хранит до 256 пар «сервер DoH и маршрут». Два фоновых работника обновляют адреса настроенных провайдеров. Готовая запись обновляется раз в час, при временном сбое доступен ещё час последнего успешного результата. Выключение последнего метода с тем же именем отменяет его обновление. При выключенном Fast DNS остаётся кеш с TTL ответа. Для автоматического bootstrap используется DoH по фиксированным IP на том же маршруте. Для имени провайдера можно явно задать bootstrap IP. Если в URL указан числовой IP, панель подключается к нему. TLS проверяет адрес или имя из URL. Серверы DoH могут выбрать HTTP/2 или HTTP/1.1 по ALPN.

Фоновое обновление также обслуживает записи, добавленные запросами клиентов после заполнения кеша, в том числе провайдеров вне первоначального списка прогрева. При смене сетевого интерфейса незавершённый запрос старого маршрута отменяется.

Одинаковые одновременные DNS-запросы с теми же параметрами маршрута и EDNS используют один запрос к провайдеру. Он продолжается, пока есть ожидающие клиенты. Каждый ответ сохраняет исходный DNS ID и написание имени клиента. Очистка кеша начинает новое поколение, поэтому завершение прежнего запроса больше его не заполняет. Ответ из кеша сохраняет название маршрута и сервера первого запроса. Отрицательный ответ учитывает SOA MINIMUM уже при первой отправке клиенту.

Фильтр DNS поддерживает доменные правила и исключения, hosts-записи, простые шаблоны, `$important`, `$badfilter` и списки включённых и исключённых типов в `$dnstype`. При проверке ответа фильтр различает тип исходного вопроса, CNAME, адресные записи и подсказки HTTPS/SVCB. Обновление списка учитывается и для запросов, начатых до обновления. API сообщает число пропущенных записей. Лимит файла списка составляет 8 МиБ. Результаты фильтрации сверены с 60 контрольными примерами из Go. На Keenetic AArch64 индекс из 100 000 обычных правил занимает 2 788 890 байт. Построение заняло 301 мс, миллион проверок (половина с совпадением) — 6,04 с.

При обновлении AdGuard с теми же байтами панель сохраняет текущий фильтр и DNS-кеш, обновляя метаданные списка. Новое содержимое заменяет фильтр и очищает кеш.

### Перенос зон с работающей Go-панели

Go сохраняет `config.routing.active=true` перед установкой правил в ядро. После успешного подтверждения в файле остаётся то же значение. Rust автоматически восстанавливает зоны после появления собственного подтверждённого журнала. [Сохранение настроек Go](../internal/services/awgroute/awgroute.go) и [подтверждение Go](../internal/services/awgroute/client.go).

На Keenetic установщик версии `2.0.0-ea-1` переносит работающие зоны Go и активный одиночный полный туннель. Go восстанавливает такой туннель при отсутствии активных зон, а также когда во всех активных зонах указаны только отдельные IPv6-адреса или IPv6-подсети и составитель IPv4-правил Go пропустил каждую зону. До переключения установщик проверяет состояние Go в течение 91 секунды, сверяет порядок зон и сохраняет их действующие IP-наборы. Для одиночного полного туннеля он сверяет цепочки `AWG2_MARK` и `AWG2_MARK6`, таблицу 998 и фактический путь помеченных пакетов. Если Go блокировал выход IPv6 через WAN для клиентов LAN, Rust восстанавливает это правило в цепочке FORWARD.

До остановки Go установщик подтверждает TCP-сокет прежней панели по процессу и системному порту. Rust сохраняет адрес привязки, включая отдельный LAN-адрес и IPv6. Вызовы API для проверки идут только к подтверждённому локальному адресу. После запуска Rust установщик сверяет действующий адрес и порт новой службы. После штатной остановки Go новая панель применяет пробную политику. Установщик проверяет подключённые туннели, ключи пиров и AllowedIPs. При включённом перехвате он также запрашивает имя действующей зоны по UDP и TCP на порту 5354 и сверяет путь ответа с настроенным выходом. Для зон с ограничением по источнику он использует локальный запрос к таблице маршрутизации с адресом источника и входным LAN-мостом. При успешной проверке установщик подтверждает политику. Последующие запуски восстанавливают её из журнала Rust. Если очистка временных файлов после подтверждения не завершилась, рабочий комплект Rust остаётся на месте. Перед следующей пакетной транзакцией установщик проверяет и удаляет старый снимок по идентификатору каталога. Для возможного отката он сохраняет подтверждённый комплект Rust.

При переходе с Go Compact установщик записывает идентификатор работающего процесса и сохраняет предыдущий комплект пакетов до замены файлов в Entware. Он оставляет выбранные дополнения и добавляет вынесенные из Go функции MTProto и захвата пакетов. При переходе с полного Go на Rust Compact сохраняются все шесть функций, выделенных в пакеты. До подтверждения маршрутов установщик проверяет адрес и порт включённого DNS-сервера, а также порты работающих MTProto и SOCKS5. При сбое прежние файлы и настройки возвращаются до запуска Go. Когда процесс уже принимает трафик на сохранённом резервном IP, Rust восстанавливает выбор по адресу и порту из проверенного снимка UAPI.

Если маршрутизация панели выключена, установщик отдельно проверяет действующие клиенты AWG до и после обновления. Для двойного туннеля он сверяет оба процесса `amneziawg-go`, ключи пиров, исходный адрес, эффективный MTU и маршрут помеченного сокета. В пробной фазе Rust читает состояние туннеля. Управление процессами передаётся панели после подтверждения обновления.

Если поздний откат прерывается после начала замены каталогов данных, повторный запуск `install.sh` сверяет журнал, каталоги и исполняемые файлы до новых операций с пакетами. Установщик завершает восстановление или подтверждает уже работающий прежний Go-процесс. Изменения в возвращённом каталоге данных сохраняются.

Перед повторным обновлением установщик проверяет, не ссылаются ли восстановленный модуль и резервная копия на один inode. Он сохраняет отдельную копию до запуска пакетного менеджера. Проверка Linux ARM64 с двумя последовательными сбоями восстановила панель, Geo и каталог стратегий, сохранила настройки и оставила Telegram выключенным.

В смешанной политике AWG2_MULTI учитывается первое совпадение в порядке зон, включая пустое назначение, `*` и ограничения по источнику. На Keenetic крупная политика хранит источники и назначения в отдельных наборах ipset. Одна зона в тесте содержит 65 536 адресов источников и 65 536 назначений. Для такой зоны достаточно одного маршрута по умолчанию на доступный туннель и семейство адресов. При включённом Kill Switch таблица содержит резервный маршрут `blackhole`, который закрывает выход при исчезновении туннельного маршрута. Правила TCP MSS на Keenetic ограничивают SYN и SYN-ACK в обе стороны значением MTU туннеля минус 40. В перенесённом `AWG2_MULTI` правила действуют для IPv4. У одиночной политики Go они действуют также для IPv6, когда он доступен. Итоговая ёмкость зависит от перекрытия зон, размера классификатора, резервов, числа DNS-записей и размера журнала. Для OpenWrt fw3/fw4 действуют прежние пределы.

Журнал отката хранит одинаковые поколения плана один раз. На поколение отведено до 12 МиБ и 262 144 развёрнутых записей, включая резервы и DNS. Перед остановкой Go проверяется, что журнал вмещает пробную и подтверждённую политику и их замену. Новый Rust читает и прежние журналы. Возврат с этого формата на ранний Rust-бинарник выполняется с резервной копией данных соответствующей версии.

На OpenWrt работающая панель Rust получает от ядра уведомление о перезагрузке fw4. Перед восстановлением она сверяет физический туннель, маршруты и состав правил. В изолированных OpenWrt 24.10.0 и 25.12.0 AArch64 релизный бинарник перенёс разрешение пересылки при переименовании зоны до и после подтверждения политики, восстановил NAT и TCP MSS после `fw4 reload` и сохранил посторонние правила обеих зон. После аварийной остановки Rust восстановит политику при следующем запуске. У Go оставшийся после аварии UCI include позволяет fw4 самостоятельно восстановить разрешения пересылки между мостами и AWG. При штатной остановке Go удаляет этот include.

Если сохранённая правка держит интерфейс заблокированным, fw4 может восстановить правила nftables для остальных туннелей. Панель проверяет журнал, IP-блокировки и действующие маршруты, включая резервные. Редактируемый интерфейс остаётся заблокированным до подтверждения правки.

Для одиночного полного туннеля AWG2_MARK после подтверждения перехода Rust повторяет проверку IPv6 через выбранный AWG-интерфейс. Она открывает привязанный к нему TCP-сокет на `[2606:4700:4700::1111]:53`, ждёт до двух секунд и сохраняет результат на 90 секунд. Для повторной пробы отдельная таблица содержит один маршрут к этому адресу. Её выбирает только локальный сокет с привязкой к данному AWG-интерфейсу. При недоступности туннельного IPv6 Rust сначала закрывает пересылку IPv6 через WAN. После восстановления сначала возвращает туннельный маршрут. В полном режиме постоянного двойного туннеля IPv4 и IPv6 заблокированы при потере выбранного внутреннего туннеля даже с выключенным Kill Switch. Для возобновления пересылки панель проверяет маршрут транспорта через заданный внешний туннель. На ядре без стека IPv6 переносится IPv4. Ошибка чтения работающего IPv6-firewall останавливает подготовку.

При ручной замене исполняемого файла сохраните резервную копию, штатно остановите Go и запустите Rust. В разделе маршрутизации AWG проверьте зоны и нажмите «Применить». Проверьте доступ к панели и нужным ресурсам через туннель и нажмите «Подтвердить» в течение 90 секунд. По истечении срока Rust снимет пробную политику. Для возврата к маршрутам Go запустите прежнюю панель с сохранённой конфигурацией.

### Маршруты по точным DNS-именам

На Keenetic с BusyBox для применения правил AWG установите `ip-full` из Entware командой `opkg install ip-full`. BusyBox на проверенной модели поддерживает только малые номера таблиц, а панель использует отдельные таблицы начиная с 17842. Для IPv6 требуются загруженные таблицы `filter`, `nat`, `mangle` и цели `MASQUERADE` и `TCPMSS` в `ip6tables`. На проверенном Keenetic эти компоненты ядра доступны. Зависимость можно докачать при настройке маршрутизации AWG.

На Keenetic перед применением туннельных правил панель сохраняет текущие параметры PPE и fast NAT. При снятии политики или штатной остановке она восстанавливает значения, сохранённые в той же загрузке ядра. Выборочное ускорение прямого трафика на KN-1012/MT7981 требует явного `N2S_AWG_SELECTIVE_ACCEL=1`, проверяемого учёта пакетов и защитных правил IPv4 и IPv6 для NFQUEUE и туннелей AWG. При недоступности этих условий панель отключает ускорение на время работы политики. На OpenWrt активный flow offload по-прежнему блокирует применение туннельных правил.

В разделе маршрутизации AWG выберите режим «По зонам» и источник «Resolve — определить IP при применении правил». Для предварительного разрешения отключите автоматическое включение поддоменов и задайте точные имена. Панель запрашивает A, AAAA или оба типа в зависимости от семейства адресов правила и туннеля. IPv4-адрес получает маршрут `/32`, IPv6-адрес — `/128`. Правило действует на все подключения к этому IP в указанной сети источника, в том числе на сайты с общим адресом.

При включённом DNS-сервере панели запросы проходят через его локальный порт с настроенными фильтрами и выбором upstream. При выключенном сервере для предварительного разрешения используются адреса из `/etc/resolv.conf`. Лимиты составляют 32 имени, до 16 адресов каждого семейства на имя и 128 различных адресов на политику. На весь снимок отводится восемь секунд. Ошибка DNS сохраняет предыдущий полный снимок.

После подтверждённой ошибки действующей DNS-маршрутизации ручное применение точных глобальных имён может обратиться за свежим ответом к управляемому резолверу напрямую. Запросы используют настроенные фильтры и маршруты DNS. Перед применением панель проверяет поколение правил, резолвер и срок действия полученных адресов.

Для подтверждённых статических правил с точными именами панель может повторно использовать проверенный набор A и AAAA, полученный при предыдущей неудачной попытке применения. Сначала она запрашивает свежие записи. Повтор возможен при таймауте после начала отправки DoH-запроса через проверенный TLS, если остальные ответы совпадают с подтверждёнными адресами. Для всего набора действует самый ранний исходный TTL и предел в 20 минут. Отрицательный ответ, другой адрес, смена правила, настроек резолвера или каталога фильтров отменяют повтор.

Если при неизменных правилах свежий полный DNS-снимок дал новые адреса, панель может повторить его применение после сбоя записи в ядро. Для этого ядро и журнал должны подтвердить восстановление прежних маршрутов. При повторе действуют исходный TTL и прежние проверки резолвера. Успешный повтор создаёт обычное пробное применение с подтверждением или автоматическим откатом.

При первой установке статических правил по точным DNS-именам повтор доступен после сбоя записи и подтверждённого возврата к пустому набору маршрутов панели. Проверяются обе доступные семьи IP, даже если правило запрашивает только одну. Посторонние записи в зарезервированных таблицах, смена загрузки ядра или конфигурации исключают повтор. Срок действия полного подтверждённого DNS-ответа отсчитывается с первого получения.

После подтверждённого отката первого применения управляемый DNS возвращает `SERVFAIL` для запросов, прошедших фильтр, включая ответы из кеша. Фильтр продолжает выдавать собственные ответы. Следующее применение может напрямую запросить свежие адреса у настроенного резолвера. Успешное применение или снятие политики восстанавливает выдачу ответов.

Такой же ответ действует после подтверждённого отката смены адресов статической зоны. Очередное фоновое обновление может обратиться к настроенному резолверу напрямую. Выдача ответов восстанавливается после проверки свежего набора адресов в подтверждённом плане.

Во время записи маршрутов управляемый DNS ждёт публикации результата в пределах общего срока запроса. Для UDP и TCP с момента приёма отводится 27 секунд, для диагностики 28 секунд. Ответы фильтра выдаются сразу. При успешной установке маршрута используется оставшийся TTL исходного DNS-ответа.

Подтверждение сохраняет адреса из пробного применения. После перезапуска панель восстанавливает их из журнала. В штатном режиме примерно раз в минуту она повторяет DNS-запросы для подтверждённой конфигурации. До проверки всех новых адресов сохраняются действующие маршруты и защита при недоступном туннеле.

### Маршруты по ответам DNS

В разделе AWG выберите «По зонам», задайте источник `dnsproxy` и добавьте, например, `*.office.example`. При применении на Keenetic панель принимает DNS-запросы с LAN-мостов `br*` по UDP и TCP, IPv4 и IPv6. Запрос на порт 53 поступает в обработчик на порту 5354 с исходным адресом клиента. Обработчик запрашивает штатный DNS роутера на `127.0.0.1:53`. Откат пробного применения и снятие политики удаляют её перенаправления. На OpenWrt включите DNS-сервер панели и укажите его LAN-адрес в настройках DNS клиентов.

После ответа прошивки прозрачный DNS ждёт завершения обновления той же политики до двух секунд. Если политика заменена, запрос со старым снимком получает `SERVFAIL`. При отсутствии ответа прошивки UDP-запрос остаётся без ответа, TCP-соединение закрывается. Маршрут привязывается к исходному адресу клиента и мосту, а ожидание учитывается в сроке действия адресов.

Прозрачный перехват обрабатывает один DNS-запрос на TCP-соединение. Для чтения запроса и записи ответа действует общий таймаут в шесть секунд. При сбое штатного DNS роутера перехват закрывает TCP-соединение или оставляет UDP-запрос без ответа. Подтверждение маршрута занимает до двух секунд. При его ошибке или задержке клиент получает SERVFAIL без адресов. Собственный DNS-сервер панели поддерживает несколько запросов на TCP-соединение.

После применения новых масок панель может использовать свежие ответы A и AAAA, которые прозрачный перехват получил до совпадения с правилом. При повторном применении учитываются исходный клиент, LAN-мост и оставшийся TTL. Смена поколения правил прерывает предыдущее применение. Панель периодически сохраняет этот кеш и восстанавливает ещё действующие записи после перезапуска демона в пределах той же загрузки роутера.

Управляемый DNS-сервер также запоминает ответы A и AAAA, полученные клиентами до появления подходящего правила. При применении правила маршрут использует тот же адрес клиента и исходный срок действия DNS-ответа. Запись действительна в памяти в пределах жизни экземпляра резолвера и текущего набора фильтров.

При подтверждённом сбое динамической маршрутизации управляемый DNS возвращает клиенту SERVFAIL. Панель может сохранить проверенный ответ от upstream для исходного клиента и применить его после успешного восстановления правил в пределах исходного TTL.

Rust читает имена из двух прежних DNS-архивов Go и разрешает их заново. Записи журнала обнаруженных имён применяются ко всем подходящим нативным явным правилам в их порядке, включая ограничения по подсетям источников. Имена из простого файла недавних DNS-ответов применяются к первому подходящему общему правилу. Управляемый DNS-сервер панели применяет настроенные фильтры, политику VPN и явные правила Shadow DNS. При выключенном сервере и действующем прозрачном перехвате запросы идут через штатный DNS Keenetic. Маршруты получают адреса и TTL свежего ответа. Если во время запроса сменились правила или экземпляр DNS-сервера, ответ отбрасывается.

Если ответ содержит CNAME без адреса, повторные запросы используют тот же резолвер и общий срок ожидания. Учитывается до 16 переходов. Маршрут сохраняется для исходного подходящего имени и действует до самого раннего истечения TTL в цепочке.

Перед запросами панель объединяет до 128 самых свежих уникальных имён из памяти и журнала. Все правила используют этот снимок. Наблюдения, сделанные во время прогрева, учитываются при следующем применении.

В режиме `resolve` маски, явное включение поддоменов или ограничение доменной зоны по источнику также включают наблюдение за DNS-ответами. Для прежних подтверждённых правил сохраняется способ разрешения из журнала вплоть до нового применения. Доступны точное имя, суффикс с границей метки, шаблоны `*` и `#` (один символ), `keyword:` и регулярные выражения. Ограничение по адресу клиента учитывается и при выдаче ответа из общего DNS-кеша. Собственный DoH или DoT клиента проходит мимо наблюдения.

Перед выдачей адреса панель проверяет цепочку CNAME, записи A/AAAA и адресные подсказки HTTPS/SVCB. Она устанавливает и проверяет маршрут, затем отдаёт ответ клиенту. При ошибке операции клиент получает SERVFAIL. Для чисто IPv4-туннеля запрос AAAA получает пустой ответ NOERROR. Срок жизни выданных адресов ограничен 300 секундами. Журнал удерживает маршрут ещё до пяти минут после этого срока, чтобы сгруппировать продления и сократить записи на накопитель. Очистка просроченных адресов и проверка резервов выполняются примерно раз в 30 секунд.

Панель раскрывает ссылки `list:`, `geosite:` и `geoip:` при подготовке маршрутов. В настройках сохраняются ссылки, а подтверждённая политика и снимок источников позволяют восстановить маршруты после перезапуска. Для действующей политики с такими ссылками панель каждые 15 минут проверяет изменение источников. При ошибке чтения или применения продолжает работать предыдущая политика. История обнаруженных доменов сохраняется в прежнем формате Go, до 512 записей на зону и 4096 суммарно. Панель записывает обновления пакетами примерно раз в 30 секунд и при штатной остановке. Восстановление архива возвращает историю без подтверждения текущих маршрутов и перечитывает сохранённую конфигурацию DNS. Как и в Go, прямое исключение для всей LAN пропускает известные общие диапазоны Cloudflare, чтобы один сайт не изменил маршрут ко всему узлу CDN. Исключение с указанной сетью источника действует в пределах этой сети.

В режиме «По зонам» можно сохранить включённый флаг `sni_routing` из Go. После применения явных зон Go останавливает прежний обработчик TLS ClientHello и использует DNS для обучения доменным маскам. В Rust такие зоны принимают ответы DNS панели, учитывают сеть клиента и направляют адреса в выбранное подключение. Для завершающей туннельной зоны `*`, `0.0.0.0/0` и `::/0` включают маршрут по умолчанию IPv4. Перед этой зоной могут стоять прямые исключения по IP и CIDR для всей сети. Эти три формы в Go имеют одно и то же значение.

Из четырёх общих буферов соединение занимает один для пакета до 128 КиБ или два для более крупного пакета. После исчерпания квоты или для пакетов свыше 256 КиБ используется потоковая отправка с продолжениями. При закрытии входа передаются уже полученные байты неполного пакета.

При закрытии клиентского потока MTProto через HTTP/2 журнал показывает статус 403, 404, 429 или 444 либо отрицательный код из тела ответа. Остальные клиенты на том же HTTP/2-соединении продолжают работать.

В сохранённых Go-профилях каждый сервер HTTP/2 имеет отдельный лимит 64 запросов и по 32 МиБ на приём и передачу. Локальное переполнение буфера закрывает затронутую сессию. Другие клиенты продолжают использовать исправный сервер. Для сохранённых профилей слот HTTP-запроса выделяется после чтения полного пакета. В пределах 4 МиБ + 256 байт из общей квоты сервера и 64 клиентов неполные пакеты могут ждать продолжения без таймера. Для остальных загрузок 180 секунд без новых данных закрывают сессию и освобождают буфер. Таймаут самого HTTP-запроса составляет 65 секунд. Если ответ в этой сессии уже поступает, автоматический повтор другого запроса ждёт его передачи клиенту. Повтор, ожидающий ответ, уступает занятый слот только при появлении другого запроса, которому нужен этот слот. В профиле `direct_wss` сохраняются общие лимиты и суммарный таймаут 65 секунд на чтение пакета.

В режиме SOCKS5 из Go ответ CONNECT приходит до подключения к назначению. Ссылка берёт имя из запроса, сохранённой настройки или исходящего маршрута роутера. Для штатной сети Telegram прокси читает ровно 64 байта предисловия и передаёт их по WSS. Внешний клиент сохранённого Go-профиля без пароля может установить проверенное WSS-соединение со штатным узлом Telegram или публичным адресом, сохранённым в настройке перенаправления этого DC. Предисловие должно соответствовать протоколу Obfuscated2. Резервное разрешение штатного имени Telegram также исключает локальные и специальные адреса. Для обычного внешнего CONNECT к произвольному назначению SOCKS5 требует аутентификацию. В IPv6 LAN принадлежность клиента к локальной подсети проверяется по адресу назначения и интерфейсу приёма.

Для обычного назначения по имени этот режим запускает попытку соединения через второе семейство IP через 300 мс или сразу после ошибки первого семейства. На все попытки действует прежний лимит в 10 секунд.

Для тестовых DC 1, 3 и 5 исполнитель MTProto использует `/apiws_test` при подтверждённом маршруте через AWG. Явный тестовый DC и принудительный тестовый режим используют один пул для каждого сочетания DC и типа трафика. В Go-профилях счётчик `ws.errors` учитывает ошибки исходящих попыток пула. Ожидание занятого слота и отказ отдельного TCP-резерва на этот счётчик не влияют. В альтернативной попытке SNI для штатных перенаправлений DC 2 и 4 допустим действительный доверенный IP SAN фактического адреса подключения. Пул HTTP/2 закрывает соединение после 90 секунд простоя с момента завершения последнего запроса.

Перед выдачей WebSocket из пула Go-профиля исполнитель проверяет двухбайтовый заголовок в пределах 2 мс. EOF в неполном заголовке и кадр закрытия исключают соединение из пула. Если истёк только срок ожидания, прочитанные байты передаются декодеру вместе с продолжением.

После временного сбоя пополнение пула Go-профиля возобновляется по истечении задержки для этого маршрута. Ближайший срок пересчитывается при завершении попытки или изменении маршрутов.

При штатном завершении входящего потока между пакетами исполнитель Go-профиля отправляет серверу пустой маскированный кадр WebSocket Close. На отправку отведено до 100 мс.

Если клиент закрыл поток в начале MTProto-пакета и исполнитель ещё не отправил ни одного его фрагмента, накопленные байты уходят отдельным зашифрованным кадром перед Close. Исполнитель учитывает их один раз.

Если часть пакета уже отправлена, исполнитель завершает сообщение кадром продолжения и затем отправляет Close. При закрытии на границе буфера последний кадр продолжения пуст. Сервер собирает те же полученные байты, что и в Go. Размер рабочего буфера составляет 16 КиБ.

Если первым закрывается сервер, исполнитель подтверждает пустой Close или отправляет исходный допустимый код. Текст причины в ответ не входит. Исполнитель отвечает, когда канал записи свободен и ожидающий кадр соответствует полученному. Для ответа действует тот же предел 100 мс.

Если запись ответа клиенту завершается ошибкой, унаследованный исполнитель отправляет серверу пустой Close при свободном канале записи. Попытка занимает до 100 мс. Исполнитель сохраняет исходную ошибку и счётчики.

Для Go-профилей журнал Telegram показывает полный сбой пополнения обычного или медиапула с номером DC и задержкой следующей попытки. Отклонённый заголовок входящего подключения записывается как предупреждение. Если запасные маршруты исчерпаны до подключения, журнал указывает DC, тип трафика и тестовый режим. Сбой фактической попытки резервного TCP-подключения записывается с номером DC и задержкой повтора. При неполной записи заголовка инициализации резервное подключение завершается ошибкой. Если не удалось обновить встроенный каталог CF обоими способами, журнал сообщает об ошибке, а исполнитель продолжает использовать предыдущий список. При потере слушателя исполнитель сообщает о сбое и повторно открывает тот же порт. Код `-404` от MTProto через HTTP/2 записывается как ошибка транспорта и по-прежнему передаётся клиенту. Исполнитель передаёт панели только проверенные структурированные сообщения.

При подключении Telegram по имени первый адрес, полученный от системного резолвера, определяет семейство первой попытки. Второе семейство начинает подключение через 300 мс или сразу, если первое исчерпало попытки. Между адресами одного семейства делится оставшееся время. Отдельной попытке выделяется не менее двух секунд, если это позволяет общий дедлайн. Это действует для обычных и защищённых WebSocket, HTTP/2, каталога CF и подключения к настроенному HTTPS-узлу FakeTLS. Для узла FakeTLS сохраняются проверка публичных адресов и предел в восемь адресов.

Исходящие соединения TCP-резерва MTProto используют системные размеры буферов и TCP_NODELAY. На поддерживаемых платформах keepalive начинает проверку после 15 секунд простоя, повторяет её через 15 секунд и допускает девять проб. Те же параметры keepalive используются в унаследованных режимах Cloudflare Worker, CF WebSocket, прямого пула Telegram WSS и CF HTTP/2 с их штатными размерами буферов.

Счётчик `h2.errors` учитывает фактические ошибки подготовки HTTP/2-соединения. Повторы во время задержки и ожидание свободного слота оставляют счётчик прежним. HTTP/2 обрабатывает готовые ответы, пока запись клиенту занята. Если сервер уже вернул ошибку транспорта, начатый кадр и код ошибки записываются клиенту в пределах общего таймаута в две секунды.

При завершении отправки со стороны клиента уже начатый зашифрованный ответ с ошибкой MTProto может завершиться в пределах исходного двухсекундного таймаута записи.

Известные имена полей сохранённых профилей Telegram читаются по правилам Go для регистра. Неверный тип известного скалярного поля в раннем повторе вызывает ошибку, даже если последнее значение допустимо. Запись использует штатные имена полей и сохраняет дополнительные поля профиля.

Панель распознаёт действующие цепочки Go `AWG2_MULTI` и `AWG2_MARK` при подготовке переноса и разрешает доменные имена конечных точек VPN перед проверкой маршрутов. Трассировка и Telegram скачиваются по отдельности в обоих вариантах. [Размеры пакетов и команды сборки](rust-compact.md#общий-исполнитель-rust).

| `aarch64-3.10_kn` | 3,69 | 6,82 | 2,34 | 4,23 |

На AArch64 четыре дополнения для прогонов, BlockCheck, стратегий и Geo занимают вместе 2,21 МиБ файлов до загрузки баз GeoSite/GeoIP. Все 28 IPK проверены по контрольным суммам, порядку каталогов в архиве, составу файлов и архитектуре ELF. На физическом устройстве проверена AArch64.

На Keenetic в отдельном корне установили базу и поочерёдно скачали все шесть финальных дополнений через `POST /api/system/install`. Штатный Entware `opkg` получил IPK по HTTP. Для каждого модуля совпала контрольная сумма установленного исполнителя. Все четыре дополнительные страницы стали доступны сразу после установки и вернули HTTP 404 после удаления пакета. Базовая страница работала на каждом шаге. Системные зависимости в этом тесте представляли локальные записи пакетов. Рабочая база `opkg` роутера сохранила прежнюю контрольную сумму.

Для загрузки обновлений и потокового замера скорости нужен системный `curl` с HTTPS. Установка движка AWG проверяет SHA‑256 архива, разрядность, порядок байтов и архитектуру ELF перед атомарной заменой файла.

Для установки из собственного репозитория укажите каталог `dist/rust-feeds/<архитектура>/<версия>/` как источник Entware. Переход с работающей Go-панели выполняет скрипт обслуживания из базового IPK. Дополнения устанавливаются из соответствующего раздела панели или командой `opkg install`. [Настройка источника Entware и смена версии](rust-compact.md#установка-из-собственного-репозитория).

Если уже установлен Go Compact, запустите `install.sh` из Rust-комплекта с `N2S_PROFILE=compact`. Скрипт сам загружает пакеты. Прямой вызов `opkg install` блокируется перед заменой старой базы, чтобы скрипт мог сохранить рабочую установку для отката.

```sh
opkg update
opkg install nfqws2-strategy-compact
N2S_PROFILE=compact sh /opt/lib/nfqws2-strategy/install.sh
```

Для перехода на конкретную сборку установщик принимает `N2S_EXPECT_PACKAGE_VERSION` и `N2S_EXPECT_VERSION`. Первая переменная задаёт точную версию IPK, вторая — ответ команды `n2s version`. Для базового пакета `2.0.0-ea-1` с раздельными модулями обе равны `2.0.0-ea-1`. Установщик сверяет их перед остановкой сервиса.

После перехода кнопка проверки рядом с версией и команда `n2s checkupdate` находят новые версии базы в настроенных источниках Entware. Кнопка «Обновить выбранные» и команда `n2s update` запускают штатный установщик, который сохраняет установленные модули и проверяет их версии. Источник должен содержать пакеты следующей версии для архитектуры роутера.

Самостоятельная Linux-сборка выпускается как архив с панелью и тремя соседними исполнителями `nfqws2-trace`, `nfqws2-blockcheck` и `nfqws2-tgws`. Самообновление панели использует отдельный `nfqws2-strategy-rust-linux-<arch>` и `SHA256SUMS` того же тега GitHub. Оно проверяет контрольную сумму, архитектуру ELF и версию. Для обновления исполнителей нужен полный архив того же выпуска. В Entware базу и дополнения обновляет `opkg`.

## Компактная установка на OpenWrt

Для роутера нужен репозиторий под его выпуск и архитектуру пакетов. На Linux-машине сборки распакуйте соответствующий OpenWrt SDK и задайте путь к нему в переменной `SDK`. В следующем примере используется цель ARM64, а `0.1.0-6` задаёт версию и ревизию локальной сборки. На роутере Rust, Node.js и SDK не требуются.

```sh
npm --prefix frontend ci
rustup target add aarch64-unknown-linux-musl
CC_aarch64_unknown_linux_musl=clang AR_aarch64_unknown_linux_musl=llvm-ar \
  N2S_COMPACT_TOOLS=shared sh scripts/build-openwrt-feed.sh "$SDK" 0.1.0-6 "$PWD/dist/openwrt-feed"
```

Сборщик читает архитектуру из SDK и проверяет класс ELF, архитектуру процессора и порядок байтов. Предусмотрены AArch64, x86-64, совместимые ARMv7 с аппаратным FPU и MIPS32r2 soft-float обоих порядков байтов. Для x86-64 используется цель `x86_64-unknown-linux-musl`. Для C-зависимостей укажите musl-компилятор в `CC_x86_64_unknown_linux_musl`.

Переменная `N2S_COMPACT_TOOLS=shared` выбирает общий исполнитель для Geo, стратегий, прогонов и BlockCheck. Без неё каждый модуль содержит собственный исполнитель. В обоих вариантах базу можно поставить отдельно. Сохраните закрытый ключ подписи SDK на машине сборки для последующих обновлений репозитория.

Распакованные файлы одной базы занимают примерно 6,84 МиБ на ARMv7, 6,85 МиБ на ARM64, 7,90 МиБ на x86-64 и 9,50–9,52 МиБ на MIPS32r2. У ARM64-сборки файлы четырёх этих модулей занимают ещё 2,21 МиБ при раздельной упаковке и 1,10 МиБ с общим исполнителем. Для одного Geo раздельная упаковка занимает 0,36 МиБ, общая — 1,08 МиБ. Базы Geo, системные зависимости и накладные расходы файловой системы в расчёт не входят.

Разместите содержимое `dist/openwrt-feed` по HTTPS. В командах ниже `FEED_URL` — адрес опубликованного вами каталога. Предварительно передайте соответствующий открытый ключ на роутер в `/tmp` через доверенный канал.

**OpenWrt с opkg** (включая 21.02 и 24.10)

```sh
opkg-key add /tmp/public-key.pub
printf 'src/gz n2s %s\n' "$FEED_URL" > /etc/opkg/n2s.conf
opkg update
opkg install nfqws2-strategy-compact
N2S_PROFILE=compact sh /usr/lib/nfqws2-strategy/install.sh
opkg install nfqws2-strategy-geo
```

**OpenWrt с apk** (25.12 и образы с тем же менеджером)

```sh
cp /tmp/public-key.pem /etc/apk/keys/n2s.pem
printf '%s/packages.adb\n' "${FEED_URL%/}" > /etc/apk/repositories.d/n2s.list
apk update
apk add nfqws2-strategy-compact
N2S_PROFILE=compact sh /usr/lib/nfqws2-strategy/install.sh
apk add nfqws2-strategy-geo
```

Последняя команда каждого примера устанавливает необязательный раздел Geo. Его также можно добавить из панели. Бинарники модулей и сжатые страницы лежат в `/usr/lib/nfqws2-strategy/modules`, данные панели — в `/etc/nfqws2-strategy`. Службой управляет procd через `/etc/init.d/nfqws2-strategy`. Повторный запуск пакетного `install.sh` обновляет установленные разделы и сохраняет выбранный порт. При перепрошивке с переходом с opkg на apk сохраните данные панели, подключите репозиторий для новой прошивки и установите выбранные пакеты заново.

Для маршрутов AWG используется действующий firewall. В fw3 панель применяет правила в зоне LAN через iptables, в fw4 — через nftables в таблице `inet fw4`. При отсутствии явно заданного WAN клиент запрашивает у netifd интерфейс маршрута к конечной точке соответствующего семейства IP. Для установки маршрутов нужен `ip-full`.

Панель определяет зону логической сети `lan` через `fw3 -q network lan` или `fw4 -q network lan`. При переименовании она снимает свои разрешения со старой зоны, проверяет туннель и маршруты и восстанавливает разрешения в цепочке новой зоны. Панель получает уведомления о перезагрузке fw4 и опрашивает fw3 каждые 10 секунд во время пробного применения. Подтверждённую статическую политику она сверяет каждые 60 секунд, динамическую или с резервным маршрутом — каждые 30 секунд. Пробное применение сохраняет исходный срок подтверждения при восстановлении правил firewall. В изолированном OpenWrt 21.02.7 AArch64 проверены переименование зоны до и после подтверждения, восстановление NAT и MSS, а также снятие правил с сохранением пользовательских записей.

В изолированных официальных ARM64 rootfs проверены обе схемы упаковки. В каждой проверке штатный менеджер принимал подписанный тестовый репозиторий, устанавливал базу и раздел стратегий, удалял раздел и освобождал общий исполнитель после последнего зависимого пакета. Отдельно проверено сохранение данных и порта при обновлении через установщик.

| Выпуск OpenWrt | Архитектура пакетов | Менеджер | Firewall в образе |
| --- | --- | --- | --- |
| 21.02.7 | `aarch64_cortex-a53` | opkg | fw3 |
| 24.10.0 | `aarch64_generic` | opkg | fw4 |
| 25.12.0 | `aarch64_generic` | apk | fw4 |
| SNAPSHOT `r38526-9a290a36d8` | `aarch64_generic` | apk | fw4 |

## Сборка и проверка

Полная нативная панель собирается командой `cargo build --release --locked -p nfqws2-strategy`. Для архива ARM64 с исполнителями, лицензиями и контрольными суммами выполните `python3 scripts/build-rust-full.py arm64 0.1.0-rust.6` с установленными целевыми библиотеками musl и настроенными `CC_aarch64_unknown_linux_musl` и `AR_aarch64_unknown_linux_musl`. Скрипт помещает архив в `dist/rust-full/0.1.0-rust.6/arm64/`. Опции запуска можно проверить на пустом каталоге с привязкой к loopback.

```sh
N2S_DATA="$(mktemp -d)" target/release/nfqws2-strategy serve -l 127.0.0.1:8090 --ignore-saved-port
```

Для компактной сборки нужны Node.js и npm, Python 3, Cargo и Rust с целевыми библиотеками musl, а также C-компилятор и архиватор для целевой платформы. Сборщик включает обязательные лицензионные тексты. Идентификатор архитектуры репозитория берётся из `opkg print-architecture` на конкретной модели.

```sh
npm --prefix frontend ci
rustup component add rust-docs rust-src
rustup target add aarch64-unknown-linux-musl armv7-unknown-linux-musleabihf
CC_aarch64_unknown_linux_musl=clang AR_aarch64_unknown_linux_musl=llvm-ar \
  sh scripts/build-rust-compact.sh arm64 aarch64-3.10_kn 0.1.0-rust.6
CC_armv7_unknown_linux_musleabihf=clang AR_armv7_unknown_linux_musleabihf=llvm-ar \
  sh scripts/build-rust-compact.sh armv7 armv7-3.2 0.1.0-rust.6
```

Пакеты и индекс создаются в `dist/rust-feeds/<архитектура>/<версия>/`. Сборщик поддерживает AArch64, ARMv7 hard-float и MIPS32r2 o32 soft-float с обоими порядками байтов. Для MIPS стандартная библиотека собирается из исходников. Команды ниже рассчитаны на Bash, LLVM и Zig 0.14.1 в PATH. Для big-endian замените `mipsel` на `mips` и подставьте архитектуру из `opkg print-architecture`. Запуск и расход памяти на конкретной модели требуют проверки на устройстве.

```bash
rustup toolchain install nightly-2026-07-11 --profile minimal --component rust-src,rust-docs
export N2S_MIPS_TARGET=mipsel
key="${N2S_MIPS_TARGET}_unknown_linux_musl"
export "CC_${key}=$PWD/scripts/rust-mips-cc.py" "AR_${key}=llvm-ar"
export "CARGO_TARGET_${key^^}_LINKER=$PWD/scripts/rust-mips-cc.py"
sh scripts/build-rust-compact.sh "$N2S_MIPS_TARGET" mipselsf-k3.4 0.1.0-rust.6
```

```sh
npm --prefix frontend run build:compact
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo test -p nfqws2-strategy --no-default-features --features compact --locked
cargo build -p nfqws2-strategy -p nfqws2-runs -p nfqws2-strategies --no-default-features --features nfqws2-strategy/compact --locked
python3 scripts/test-rust-panel.py --panel target/debug/nfqws2-strategy --runs target/debug/nfqws2-runs
python3 scripts/test-compact-feed.py
sh packaging/test-compact.sh
```

Для сборки `0.1.0-rust.6` прошли 353 теста Cargo workspace, 129 тестов компактной панели и 343 теста интерфейса. Эталонные полная и компактная сборки Go прошли свои тесты. Сквозные тесты запускают панель во временном каталоге на случайном локальном порту. Они проверяют историю и отмену HTTPS-прогонов, подключение и удаление исполнителя, сохранение списка после перезапуска, смену порта и совместимость резервной копии с Go. Для проверки пакета с настоящими ELF используйте `scripts/test-compact-feed.py --verify-native <каталог-фида> <каталог-бинарников>`.
