# NFQWS2 Strategy Selector для Keenetic/Netcraze и OpenWrt

Веб‑инструмент для **автоматического подбора рабочих стратегий обхода DPI** для
[`nfqws2-keenetic`](https://github.com/nfqws/nfqws2-keenetic) (движок
[zapret2](https://github.com/bol-van/zapret2), Lua). Запускается прямо на роутере,
тестирует стратегии в несколько потоков на ваших списках доменов/IP, сохраняет
только те, что реально работают (есть ответ и нет обрыва на 16 КБ), и сортирует
их по скорости.

> ⚠️ При ручной установке движка нужен пакет **`nfqws2-keenetic`** (движок
> zapret2) и `iptables`. Единый `install.sh` ниже сам добавляет пакет и
> его зависимости; на Keenetic/Entware файлы находятся под `/opt`, на OpenWrt —
> в системных путях (`/usr/bin/nfqws2`, `/etc/nfqws2`).

## Возможности

- **Веб‑интерфейс** — один статический бинарник со встроенным UI и без отдельного
  веб-сервера. Светлая и тёмная темы shadcn **Neutral / Rhea**, встроенный **Inter**,
  малые скругления и адаптивные элементы на Base UI. Во всех разделах используются
  общие выпадающие списки Select и переключатели Switch в стиле Rhea, с управлением
  с клавиатуры, подписями для программ чтения с экрана и состояниями фокуса и ошибок.
- **Дашборд и мониторинг** — главная страница со сводкой (статистика TG WS Proxy,
  активные соединения, пакеты DPI‑движка очереди NFQUEUE, трафик WAN) и **живыми
  графиками нагрузки**; вкладка «Соединения» (живой conntrack с фильтром и
  сортировкой) и «Активность устройств» — что устройства LAN не могут открыть
  (кандидаты на подбор стратегий, отправляются в прогон одной кнопкой). Для отладки
  соединений у каждого устройства — **трассировка 30 с** (таймлайн conntrack) и
  **захват пакетов `.pcap`** (`tcpdump`, ставится по запросу), открываемый в Wireshark.
- **Логи** — живой просмотр логов сервиса по модулям (включая TG WS Proxy), с
  фильтром, паузой и авто‑прокруткой.
- **Система** — настройка портов веб-панели и DNS-сервера, отключение авторизации
  (с подтверждением) и логирования.
- **Списки** доменов и IP/CIDR; к каждому списку прикрепляются найденные ранее
  рабочие («базовые») стратегии.
- **Прогоны в несколько потоков** — выбираете число потоков, стратегии тестируются
  параллельно (каждый поток — изолированная песочница).
- **Изоляция трафика** — основной сервис nfqws2 продолжает работать, тестовый
  трафик отводится отдельными правилами iptables (сеть не нарушается во время прогона).
- **Метрики и сортировка** — задержка (TTFB), пропускная способность (КБ/с) и
  комбинированный «коэффициент скорости»; таблица сортируется по любой колонке.
- **Свои блобы** — загрузка собственного fake‑payload, **создание `ClientHello`**
  (снять с трафика устройства через `tcpdump` или сгенерировать по домену) и
  **корзина** (удаление в корзину с восстановлением).
- **Применение** найденной стратегии в основной конфиг nfqws2 (с резервной копией).
- **Авторизация** по логину/паролю роутера (как в nfqws-keenetic-web). Отключение — `N2S_NOAUTH=1`.
- **Выбор блобов для прогона** — отмеченные блобы загружаются во все тестируемые стратегии.
- **GeoSite/GeoIP** — загрузка `geosite.dat`/`geoip.dat` или текстового списка и импорт категории в тестовый список.
- **DNS (DoH/DoT)** — список шифрованных DNS (Google, Cloudflare, Comss, Yandex,
  xbox-dns, GeoHide, AdGuard и свои). В прогоне можно прогнать стратегии через
  каждый выбранный DNS — в результатах видно, какой DNS открыл доступ.
- **Telegram-прокси** (вкладка «Telegram», подвкладки **MT Proto** и **SOCKS5**) —
  два взаимозаменяемых прокси прямо на роутере: **MTProto → WebSocket** и **SOCKS5**
  (на базе TGLock). Оба туннелируют трафик Telegram по WSS к `web.telegram.org`
  (обход блокировки по IP); по умолчанию выключены. SOCKS5 опционально защищается
  логином/паролем. MTProto-компонент синхронизирован с **Flowseal TG WS Proxy
  v1.10.4**: проверка TLS для обычных WSS-подключений, несколько CF/Worker-доменов,
  резервный plain-WS режим на порту 80 для CF/Worker, ежечасное обновление резервных
  доменов и поддержка тестовых DC. Сертификаты Entware подхватываются автоматически;
  повторное использование TLS-сессий и ограничение одновременных подключений снижают
  нагрузку при прогреве пула. На маломощном роутере можно начать с размера пула `1`
  в настройках MTProto. Старые секреты, порты и DC-редиректы сохраняются.
  [Ревизия и границы переноса](internal/services/tgws/UPSTREAM.md).
- **Управление NFQWS2** (вкладка «Сервисы → NFQWS2») — отдельные поля стратегий и
  полный конфиг, переключатель `auto` / `list` / `all`, подсветка аргументов и Lua,
  проверка и исправление путей. File Explorer с папками, Drag & Drop, меню ПКМ,
  датами изменения и защитой критичных файлов; ZIP-экспорт, импорт и архивы стратегий.
  Версии движка и пакета показаны отдельно; обновление пакета через `opkg`/`apk`
  предлагается только по подтверждённой установленной версии и новому релизу.
  «Применить (reload)» по `SIGHUP` перечитывает списки без обрыва очереди.
  Полноценная замена стороннего `nfqws-keenetic-web`.
- **Установщик / обновление / удаление**, мульти‑арч сборки в GitHub Releases.
- **AmneziaWG 3.1** — развёртывание VPS по SSH, импорт AWG/WireGuard/WARP,
  несколько туннелей, правила маршрутизации и автовосстановление соединений,
  резервные подключения, учёт поддоменов и перенос всех правил между роутерами.
- **DNS Server** — DoH через NFQWS/AWG/WARP, кэш ответов, фильтр AdGuard,
  управляемый планировщик и экспорт/импорт настроек. **Shadow DNS** направляет
  домены из списка масок к автоматически найденному DNS WAN.

## Установка

Одна команда для **Keenetic/Netcraze с Entware, OpenWrt до 24.10 и OpenWrt 25+**.
Скопируйте блок целиком в SSH-оболочку `root`. Она сама выбирает пакетный менеджер,
готовит HTTPS и запускает установку. Номер версии и архитектуру подставлять не нужно.

```sh
sh -c '
set -e
url=https://omn1z.github.io/nfqws2-keenetic-strategy-selector/install.sh
if [ -f /etc/openwrt_release ] || { [ -f /etc/rc.common ] && [ -d /etc/init.d ]; }; then
  if command -v apk >/dev/null 2>&1; then
    apk --update-cache add ca-bundle ca-certificates curl
  else
    opkg update
    opkg install ca-bundle ca-certificates curl
  fi
  client=curl
else
  export PATH="/opt/bin:/opt/sbin:$PATH"
  opkg update
  opkg install ca-certificates wget-ssl
  client=wget
fi
f=$(mktemp /tmp/n2s-install.XXXXXX)
trap "rm -f \"$f\"" 0
if [ "$client" = curl ]; then
  curl -fSL --proto "=https" --proto-redir "=https" --connect-timeout 15 --max-time 180 -o "$f" "$url" ||
  curl -4 -fSL --proto "=https" --proto-redir "=https" --connect-timeout 15 --max-time 180 -o "$f" "$url"
else
  /opt/bin/wget --https-only --max-redirect=0 -T 30 -t 2 -O "$f" "$url"
fi
test -s "$f"
sh "$f"
'
```

Установщик и бинарники панели загружаются с **официального сайта проекта
на GitHub Pages**, без перенаправления на `github.com` или
`release-assets.githubusercontent.com`. Перед запуском проверяются SHA-256
оригинальных файлов релиза. Зависимости загружаются из настроенных репозиториев
прошивки/Entware, а NFQWS2 — из его официального репозитория `nfqws.github.io`.
Доступ к этим адресам всё ещё необходим. Проверка сертификатов HTTPS включена.

### Keenetic/Netcraze и другие системы с Entware

Сначала установите [Entware](https://github.com/Entware/Entware/wiki).
На Keenetic/Netcraze включите компонент **«Модули ядра подсистемы Netfilter»**
в настройках компонентов прошивки. Команду выше запускайте в оболочке Entware,
а не в штатной CLI KeeneticOS: обычно SSH на порт `222`, пользователь `root`.
Подготовка роутера также описана в [инструкции NFQWS2](https://github.com/nfqws/nfqws2-keenetic).

Команда использует Entware `wget-ssl`; вручную удалять `wget-nossl` не нужно.
Если старый `curl` на ARM64 падает с `Segmentation fault`, загрузчик использует
GNU `wget` из Entware. Переносить бинарник с компьютера не требуется.

### OpenWrt до 24.10 включительно — opkg

Запустите ту же команду в SSH-оболочке OpenWrt. Она использует `opkg` для
подготовки `ca-bundle`, `ca-certificates` и `curl`; единый установщик затем
доустанавливает зависимости движка и панели.

### OpenWrt 25+ и Snapshot с apk

Используйте ту же команду. Если установлен `apk`, подготовка выполняется через
`apk --update-cache add ca-bundle ca-certificates curl`. Выбор зависит от
фактического пакетного менеджера, а не только номера прошивки.
Удалять или заменять системный `wget`/`uclient-fetch` не требуется.

### После установки

Откройте `http://<IP‑роутера>:8090`. Для проверки версии выполните
`/opt/usr/bin/n2s version` на Entware или `/usr/bin/n2s version` на OpenWrt.

Единый установщик добавляет репозиторий NFQWS2 (на OpenWrt — с ключом
проверки подписи), устанавливает движок и панель. На OpenWrt он также устанавливает
модули Netfilter/IPSet/TUN и регистрирует сервис через `procd`.
Повторный запуск команды обновляет панель и сохраняет пользовательские конфиги
и списки. После выпуска нового стабильного релиза сайт установки обновляется
автоматически; пересборка бинарников для зеркала не выполняется.

Сервис и данные выбираются автоматически:

- Keenetic/Entware: `/opt/etc/init.d/S52nfqws2-strategy` и `/opt/etc/nfqws2-strategy/`;
- OpenWrt: `/etc/init.d/nfqws2-strategy` и `/etc/nfqws2-strategy/`.

### Если не удаётся скачать установщик

- Ошибки `Connection reset by peer` или несовпадения имени сертификата сами
  по себе не доказывают блокировку провайдером. Команда выше использует другой
  адрес доставки, но не может исправить любую проблему доступа к сети.
- Если уже `apk --update-cache add` или `opkg update` не может скачать индексы,
  сначала восстановите доступ к штатным репозиториям.
- Не добавляйте `-k` или `--no-check-certificate` при скачивании установщика.
- Пустой или недокачанный файл не запускается: команда завершается ошибкой,
  а не молча передаёт пустой ответ в `sh`.

Для диагностики OpenWrt сохраните вывод ошибки и следующих команд. Последняя
команда выполняется, если `curl` уже установлен:

```sh
cat /etc/openwrt_release
date
nslookup omn1z.github.io
ip -4 route
curl -V
curl -4 -vI --connect-timeout 15 --max-time 30 https://omn1z.github.io/nfqws2-keenetic-strategy-selector/install.sh
```

## Использование

1. **Списки** → создайте список, вставьте домены (по одному в строке), сохраните.
2. **Прогон** → задайте число потоков, при желании выберите конкретные стратегии
   (по умолчанию — все), нажмите «Запустить». Прогресс и результаты обновляются вживую.
3. **Результаты** → таблица сортируется по задержке / скорости / коэффициенту.
   Рабочие стратегии (зелёные, прошли все цели) автоматически сохраняются в список.
4. **Применить** → понравившуюся стратегию можно записать в `nfqws2.conf`
   (создаётся бэкап `*.n2s.bak`) и при желании перезапустить сервис.
5. **Блобы** → вкладка для загрузки своих fake‑payload; путь подставляется в
   стратегию как `--blob=имя:@/путь`.

## Как это работает

Каждый поток («песочница») получает отдельный номер очереди NFQUEUE, диапазон
исходных портов и временные цепочки iptables. Тестовые соединения помечаются
connmark `0x20000000`, поэтому основной nfqws2 (очередь 300) их игнорирует, а
тестовый экземпляр nfqws2 с проверяемой стратегией обрабатывает только их.
HTTP‑клиент скачивает тестовый URL через песочницу, измеряет байты/время и ловит
обрыв на ~16 КБ. По завершении все правила и процессы убираются.

## DNS Server

Отдельный локальный DNS-сервис в меню **«Сервисы → DNS Server»**. По умолчанию
выключен. Его включение не меняет DNS роутера или устройств: клиентские настройки
переключаются отдельно, когда вы готовы.

Для LAN-адреса `192.168.3.1` адрес подключения по умолчанию:

| Протокол | Адрес |
| --- | --- |
| Обычный DNS, UDP и TCP | `192.168.3.1:5355` |

Адрес LAN определяется автоматически. Укажите IP и порт в настройках **обычного
DNS** клиента. Локальный сервис принимает DNS по UDP и TCP без TLS: установка
сертификатов не нужна, локальных DoH/DoT/DoQ-адресов нет. Записи `192.168.3.1:5355`
в разделе DoT и `https://192.168.3.1:5355` в разделе DoH Keenetic не подключают
этот сервис: удалите их и настройте обычный DNS.

Порт DNS и порт веб-панели меняются в **«Система → Порты»**. По умолчанию панель
использует порт `8090`, DNS-сервис — `5355`. Порт `53` обычно занят встроенным DNS
роутера. Если устройство принимает только IP без порта, оно использует `53`:
оставьте IP роутера как DNS устройства и направьте встроенный DNS-прокси Keenetic
на локальный сервис. Для этого в **штатной CLI KeeneticOS**, не в оболочке Entware
`root`, выполните команды с адресом из карточки **«Подключение Keenetic и устройств»**:

```text
ip name-server 192.168.3.1:5355
system configuration save
show ip name-server
```

Для другого LAN-адреса или порта замените `192.168.3.1:5355` адресом из панели.
[Справка Keenetic Hopper](https://support.keenetic.com/hopper/kn-3811/en/19726-setting-a-non-standard-port-for-a-dns-server.html)
подтверждает синтаксис `ip name-server {address[:port]}`. Устройства, где можно
указать порт DNS, могут обращаться к этому адресу напрямую. Добавление сервера
в Keenetic само по себе не делает его единственным: DNS роутера может одновременно
использовать адреса провайдера, другие ручные серверы, DoT/DoH и профили
интернет-фильтрации. Если нужен только локальный сервис, проверьте и отключите
конкурирующие источники вручную.

На других платформах, где порт `53` действительно свободен, можно перевести
локальный сервис на него. Настройка клиента должна соответствовать выбранному порту.
Порты применяются после сохранения; при смене порта панели интерфейс открывает
новый адрес. Сохранение порта DNS не включает выключенный сервис.

На **OpenWrt 24/25+** в DNS Server доступна карточка **«DNS OpenWrt»**.
Сохраните настройки, включите сервис, выберите WAN-интерфейс и нажмите
**«Подключить DNS Server»**. Если настроено несколько экземпляров dnsmasq,
выберите тот, который обслуживает нужную сеть. Перед применением панель
проверяет ответы локального DNS по UDP и TCP.

В выбранном интерфейсе автоматически отключается DNS от провайдера (`peerdns=0`)
и задаётся **Use custom DNS servers** с IP локального DNS. Поскольку это поле
не поддерживает порт, выбранный dnsmasq дополнительно пересылает обычные запросы
на фактический адрес и порт DNS Server и перестаёт брать upstream из resolv-файла.
Правила dnsmasq для отдельных доменов сохраняются. Изменение распространяется
на все сети, обслуживаемые этим экземпляром dnsmasq; DNS, вручную заданный
на устройствах, не перехватывается. Shadow DNS продолжает читать полученные
от провайдера адреса из данных OpenWrt.

Кнопка **«Восстановить прежний DNS»** возвращает сохранённые значения этих
настроек. Они также восстанавливаются перед отключением DNS Server, сменой
его адреса/порта и удалением панели. После смены адреса или порта подключите
сервис повторно. Обычный перезапуск и обновление сохраняют привязку.
При обнаруженном конфликте со сторонними изменениями применение или
восстановление останавливается с пояснением, резервная копия сохраняется.
Не меняйте эти параметры одновременно в LuCI/SSH и панели: общей транзакционной
блокировки между ними нет. При применении dnsmasq перечитывает конфигурацию,
поэтому возможна короткая пауза в DNS-запросах.

В блоке **«Специальные DoH и домены»** сначала выбирается DoH-сервер или пул,
затем ему назначается один домен или список: по строкам, через запятую или точку
с запятой. По умолчанию одна группа объединяет `claude.com`, `claude.ai`, `grok.com`
и их поддомены под `https://xbox-dns.ru/dns-query`. Существующие правила с одинаковым
пулом и настройками автоматически отображаются одной группой. Включение группы
и обработка поддоменов настраиваются сразу для всего списка.
Остальные имена используют настраиваемый пул по умолчанию. В каждом пуле может
быть до восьми DoH-серверов: их можно добавить вручную или выбрать несколько
из существующего списка на вкладке «DNS». Домены группы используют только
её пул, без подмешивания серверов из общего пула. Побеждает самое точное
совпадение домена; выключенные группы пропускаются. Передаются все обычные типы
DNS-записей, включая A, AAAA и HTTPS; ответы кэшируются по TTL, а отсутствие
имени или записи — по подтверждению SOA.
От роутера к выбранному DoH-провайдеру запросы идут по HTTPS с проверкой
подлинности его сертификата.

Запрос без ответа в кэше направляется к провайдерам подходящего пула через
маршруты выбранного режима. **«NFQWS и VPN»** запускает NFQWS вместе с выбранными
AWG/WARP; **«Только VPN (AWG/WARP)»** исключает NFQWS и прямое соединение. В режиме
выбора подключения **«Авто»** участвуют все доступные включённые туннели, включая
WARP. Можно выбрать один конкретный туннель; в режиме «NFQWS и VPN» можно также
выключить VPN и использовать только NFQWS. Первый успешный ответ сразу
возвращается клиенту, оставшиеся попытки отменяются. Медленный или заблокированный
маршрут не задерживает ответ другого маршрута. Каждый новый запрос снова пробует
все выбранные маршруты; таймаут ограничивает каждую попытку отдельно. Если в
режиме «Только VPN» туннель недоступен, новые запросы без ответа в кэше завершаются
ошибкой DNS, без перехода на NFQWS или прямой канал.

Каждая пара «DoH-сервер + маршрут» участвует отдельно. Корректный ответ NXDOMAIN
тоже считается ответом DNS; таймауты,
ошибки HTTPS, SERVFAIL и REFUSED не могут выиграть гонку. Кэшированный ответ
возвращается без новых сетевых запросов. Текущая интеграция NFQWS обрабатывает DoH
на HTTPS-порту 443; для нестандартного порта используются выбранные AWG-подключения.

Для **Cloudflare только через VPN** оставьте в пуле по умолчанию один адрес
`https://1.1.1.1/dns-query`, выберите «Только VPN (AWG/WARP)» и нужное VPN-подключение
или «Авто». По умолчанию группы `claude.com`, `claude.ai` и `grok.com` используют
`https://xbox-dns.ru/dns-query` вместо общего пула; удалите эти группы или замените
их DoH, если Cloudflare должен отвечать для всех доменов. После сохранения проверьте
в карточке **«Проверка DNS»** домен из общего пула и отдельно домен специальной
группы: маршрут должен быть AWG/WARP, а сервер — выбранный DoH.

### Редактор и архивы NFQWS2

В разделе **Сервисы → NFQWS2** автоматика находится в отдельной вкладке.
Конфиг можно редактировать целиком или отдельными полями: параметры запуска,
базовая стратегия, QUIC, UDP, пользовательские стратегии, IPSET и режим работы.
Режим выбирается переключателем **`auto` / `list` / `all`**: автоматическое
ведение списка, работа по спискам или обработка всего подходящего трафика.
Изменение режима сохраняет дополнительные аргументы. Сложные shell-конструкции
редактируются в полном файле, чтобы форма не меняла порядок их выполнения.

Редактор подсвечивает Shell и Lua, а внутри отдельных стратегий различает
флаги NFQWS, числа, пути, переменные и параметры Lua. Доступны поиск, отмена
правок и сохранение сочетанием клавиш; смена темы сохраняет историю правок.
В полном конфиге `TCP_PORTS` и `UDP_PORTS` отдельно подсвечиваются номера,
запятые и границы диапазонов `:`.
Литеральные пути к файлам NFQWS проверяются на роутере: наведите курсор на
подчёркнутый путь, чтобы исправить его, либо примените все предложенные замены
между `/opt/etc/nfqws2` и `/etc/nfqws2`. Подстановки shell не исполняются и не
переписываются. Если файл отсутствует и после исправления пути, загрузите его
через **File Explorer**.

File Explorer показывает дерево папок и путь к открытому каталогу. Файлы можно
перетаскивать в текущую папку или на папку в списке; загрузка папки сохраняет
вложенные файлы в поддерживаемых разделах. ПКМ и кнопка **`···`** открывают
действия: редактирование, скачивание и удаление. Удаление и замена файла с
существующим именем требуют подтверждения; основной конфиг защищён от удаления.
Переход по папкам сохраняет открытый черновик редактора.

В проводнике и редакторе списков доступны категории **«Текущие»** и
**«Оригинальные»** (`.list-opkg`, включая `.gz`). Переключение категории
сохраняет открытый черновик. В редакторе **«Дедуп поддоменов»** удаляет обычные
записи, уже покрытые существующим родительским доменом: `example.com` позволяет
убрать `api.example.com`. Новые родительские домены не создаются. Точные `^`-правила,
комментарии, неизвестный синтаксис и порядок оставшихся строк сохраняются.
Результат меняет только черновик, отменяется через **«Отменить»** или Ctrl+Z
и записывается на роутер кнопкой **«Сохранить»**. Неоднозначный формат файла
оставляется без изменений с предупреждением.

Столбец **«Изменён»** показывает дату и время из файловой системы роутера в
часовом поясе браузера; наведите курсор для точного времени с секундами и зоной.
На узком экране дата находится под именем. Время папки относится к самому
каталогу и не означает последнее изменение любого вложенного файла. Разделы
конфигов и shell-скриптов отображают время общей физической папки конфигурации.

Вкладка **Архивы** экспортирует ZIP с `nfqws2.conf`, `lists/`, `blobs/`, `lua/`
и `scripts/`; при импорте достаточно одного `nfqws2.conf`. Содержимое архива
показывается перед импортом, а для userlist/autolist нужно выбрать, сохранить
свои списки или применить входящие. Перед импортом автоматически сохраняется
текущая стратегия. Именованные архивы можно создавать перед экспериментами
и восстанавливать позже. Импорт сохраняет файлы; новую стратегию запускает
кнопка **Перезапустить** после проверки конфига.

### Shadow DNS

Включите **Shadow DNS**, чтобы выбранные домены разрешались напрямую через обычный
DNS от WAN. Правила вводятся обычным списком, по одному на строку: `*.ru`,
`*.рф`, `*.vk.*`, `*.avito.*`. Начальное `*.` включает сам домен и все его
поддомены; звёздочка в остальных позициях заменяет одну полную часть имени.
Например, `*.vk.*` подходит для `vk.com` и `api.vk.ru`, но не для `notvk.com`.
Совпадения проверяются по границам DNS-меток, без перебора всего списка при
каждом запросе. При обновлении старых настроек Shadow DNS выключен.

DNS определяется автоматически через KeeneticOS на Keenetic или `ubus` на
OpenWrt 24/25+, включая полученные от DHCP, но исключённые из штатного DNS
адреса. Ручного ввода нет; адреса из старых настроек игнорируются. Адрес самого
роутера запрещён, чтобы не создать петлю. Сервис не подставляет публичный DNS
вместо отсутствующего адреса провайдера. Несколько адресов проверяются по
порядку в пределах общего таймаута запроса.

На Keenetic системный `ndmc` запускается с библиотеками прошивки, чтобы
библиотеки Entware не мешали чтению DNS. Если журнал DHCP уже очищен и адрес
DHCP-сервера ещё неизвестен, сервис запрашивает DNS через DHCPINFORM на
подтверждённом внешнем Ethernet-интерфейсе. Такой запрос не обновляет аренду
и не меняет IP роутера. Ответ кешируется на 5 минут; после неудачной попытки
повтор разрешён через 30 секунд. Поддержка DHCPINFORM зависит от DHCP-сервера
провайдера. При сбое самого `ndmc` панель показывает ошибку чтения KeeneticOS.

Shadow DNS имеет приоритет над группами DoH, в том числе при режиме «Только VPN».
Только выбранные DNS-запросы направляются через отдельную таблицу WAN; правила
маршрутизации сайтов и VPN-подключения сохраняются. AdGuard, общий кэш ответов и
DNS-обучение AWG работают как раньше. При недоступности DNS провайдера клиент
получает ошибку, без перехода к VPN/DoH; фоновые проверки планировщика также
не отправляют выбранные домены в DoH. Источник ответа и отдельный счётчик
отображаются в панели. Настройки Shadow DNS включены в экспорт и импорт.

Повторный запрос с тем же именем, типом и параметрами DNS получает ответ из кэша,
пока не истёк TTL. Настройка времени хранения — верхний предел, а не продление
коротких TTL сервера. A, AAAA и HTTPS хранятся отдельно. Для ответа из кэша
название исходного сервера в журнале не означает новый запрос к нему. Поэтому
DNS провайдера видит выбранные домены только при фактических обращениях наружу.

### Блокировка рекламы и трекеров в DNS Server

В карточке **«Блокировка рекламы и трекеров»** включите блокировку и сохраните
общие настройки DNS. Единственный загружаемый источник — официальный
**AdGuard DNS filter**. Он выбран заранее, но блокировка остаётся выключенной.
Снимите флажок AdGuard, чтобы использовать только собственные правила и исключения.
В карточке показаны ссылка на источник, количество загруженных правил и дата
обновления. Кнопка **«Обновить AdGuard»** запускает загрузку по сохранённой
настройке; состояние и ошибки появляются в той же карточке. Фильтр обновляется
автоматически раз в сутки. Загрузка использует выбранные DNS-маршруты и предпочитает
VPN. В режиме «Только VPN» загрузка не переходит на WAN; при ошибке остаются
последние успешно загруженные данные.

При загрузке настроек прежние источники автоматически заменяются на AdGuard.
Включение блокировки, собственные правила, исключения и остальные настройки DNS
сохраняются. Если загружаемый фильтр уже был снят, остаются только ручные правила.

Фильтр проверяет запрошенное имя до обращения к DoH, затем CNAME и IP-адреса
в ответе, включая IP-подсказки HTTPS/SVCB. Проверяются только записи, относящиеся
к запрошенному имени и его цепочке CNAME. Проверка действует и для ответов из кэша:
обновлённый фильтр применяется сразу. Исключение для исходного домена разрешает
весь его ответ. Журнал и проверка DNS показывают конкретное заблокированное имя
или IP. Проверка поддерживает A, AAAA, CNAME, HTTPS и SVCB.

При обновлении без изменений или редактировании собственных правил используется
уже загруженный движок AdGuard. Изменённый фильтр сначала компилируется отдельно
и только затем заменяет рабочий; при ошибке остаётся прежний фильтр.

Ручные правила указываются по одному на строку: `ads: example.com`,
`trackers: *.metrics.example.com` или `mixed: tracker.example.org`. Без префикса
используется категория `trackers`. Имя `example.com` блокирует домен вместе с
поддоменами, а `*.example.com` — только поддомены. Для узкого совпадения можно указать
`ads: *-netseer-ipaddr-assoc.xy.fbcdn.net`, не блокируя весь `fbcdn.net`.
Исключения указываются отдельными строками без категории и разрешают домен вместе
с поддоменами; `*.example.com` в исключениях равнозначно `example.com`. Правила применяются к DNS-запросам
клиентов этого локального сервера до обращения к внешнему DoH.

В **«Проверке DNS»** заблокированный домен отмечается как локальная блокировка,
а не как ошибка DoH-провайдера. Журнал показывает категорию, источник и правило.
Счётчики рекламы, трекеров и общей категории AdGuard считают **DNS-запросы с запуска
DNS-сервера**, а не показанные рекламные баннеры. Сохранение настроек перезапускает
DNS-сервер и сбрасывает эти счётчики. AdGuard не разделяет свои
попадания на рекламу и трекеры; они входят в категорию «Реклама и трекеры».
Если устройство использует другой DNS, эти
счётчики не охватывают его запросы; для общего применения настройте DNS на
Keenetic и устройствах, как описано выше.

Настройка **fast-dns** включена по умолчанию: IP-адреса DoH-серверов заранее
загружаются в память и обновляются в фоне раз в час. Одновременные запросы одного
адреса используют общий результат; прогрев выполняют не более двух работников.
При ошибке обновления последний известный IP доступен ещё до часа, а повторная
попытка выполняется через минуту. Ошибка подключения также запускает обновление
с защитой от частых повторов. Адреса учитываются отдельно для каждого маршрута;
вручную заданные IP и DoH с IP в URL имеют приоритет. Кэш ограничен 256 записями
«имя DoH + маршрут», по 16 IP в каждой, и не изменяет проверку сертификатов HTTPS.
Перезапуск сервиса запускает новый прогрев. При выключенном fast-dns работает
обычный кэш bootstrap по TTL, максимум пять минут. Кэш ответов для устройств
и его кнопка очистки на эти адреса не влияют.

Переключатель **«Планировщик DNS»** включён по умолчанию и применяется кнопкой
**«Сохранить»**. При выключении фоновые проверки, сбор оценок и ранжирование
останавливаются; обычные запросы продолжают одновременно пробовать допустимые
пары DoH и маршрутов в порядке настройки. **fast-dns** управляется отдельно и
продолжает прогревать адреса провайдеров, если включён.
Если в конкретном пуле остаётся только одна доступная включённая пара,
планировщик автоматически пропускает её оценки и фоновые проверки. Появление
второго допустимого варианта возобновляет работу без повторного переключения.
Независимые доменные пулы с одним вариантом не считаются конкурентами друг друга.

Блок **«Планировщик»** по умолчанию показывает общий пул DNS. В режиме
**«По домену»** можно посмотреть очередь для конкретного имени. Для каждого
варианта показаны DoH-провайдер, маршрут, задержка успешных ответов, надёжность,
ошибки и составляющие оценки.
Переключателем в строке можно выключить конкретную пару **«DoH + маршрут»**:
например, запретить NextDNS через NFQWS, сохранив его работу через WARP и другие
AWG-туннели. Отключение действует для этого полного URL DoH и маршрута во всех
пулах, включая доменные. Настройка применяется сразу, сохраняется после
перезапуска и не сбрасывает кэш или статистику. Выключенная строка остаётся
в таблице для повторного включения, но не участвует в запросах и фоновых проверках.
При работающем планировщике более высокая оценка даёт варианту свободный слот
раньше. Оценка равна
`100 × надёжность − min(80, задержка / 20) − min(100, 20 × ошибок подряд)`.
Первый завершённый замер задаёт фактическую надёжность и задержку; следующие
сглаживаются по правилу 80/20. Ошибки снижают приоритет, отмена после победы
другого варианта не считается ошибкой и не обновляет время последнего замера.
Раз в пять секунд планировщик выбирает один вариант для независимой фоновой
проверки: сначала без результата, затем с самым старым замером (от минуты).
Такая проверка доводится до ответа или таймаута, даже если клиент уже получил
ответ другого сервера. Она занимает один из общих 32 слотов и пропускается,
когда они заняты. Поэтому быстрый вариант из конца очереди может снова стать
лидером. После пяти минут без результата устаревшая оценка заменяется новым
измерением. Фоновые запросы не заполняют кэш ответов, статистику клиентов или
AWG-маршрутизацию: общий пул проверяется вопросом NS корневой зоны, специальные
пулы — доменом из своей группы. В таблице видны время последнего результата,
состояние и счётчики фоновых проверок. Оценки сохраняются при изменении настроек
DNS; после перезапуска панели варианты измеряются заново.

**«Журнал DNS»** показывает ответы, кэш, общие ответы, отмены и ошибки. Логирование
включено по умолчанию и переключается отдельно, без перезапуска DNS. Журнал
хранится только в памяти; сериализованные записи занимают не более 128 КиБ, старые
записи удаляются при добавлении новых. Доступны пауза просмотра, фильтр и очистка.
Отменённые попытки одного запроса объединяются в одну запись со счётчиком;
успешный ответ не дублируется отдельной записью успешного маршрута. Короткие
строки и значки заменяют повторяющиеся пояснения, соседние отмены показываются
рядом со своими доменами. Ошибки сохраняют причину, а подробности запроса доступны
в раскрывающейся строке. Отмены не ухудшают оценки планировщика и не задерживают
возврат первого ответа.
Перезапуск панели очищает журнал, а перезапуск одного DNS-сервиса сохраняет его.

В журнале и проверке DNS видны отправитель и транспорт UDP/TCP/API. Адрес
отправителя — фактический сосед DNS-сервера: если встроенный DNS Keenetic
пересылает запросы от своего имени, строка «Роутер / DNS-посредник» не раскрывает
исходное устройство или вкладку браузера. Запрос к домену сам по себе не
подтверждает, что сайт сейчас открыт. Проверки из панели помечены отдельно.
Заполненный журнал использует кольцевой буфер: добавление новой записи не
сдвигает все старые записи. Панель получает только новые события по курсору и
удаляет из своей истории уже вытесненные записи. Идентификатор экземпляра журнала
отличает перезапуск панели от обычной очистки и предотвращает смешивание истории.

Кнопка **«Экспорт сохранённых настроек»** скачивает JSON со всеми сохранёнными
параметрами DNS Server: адресом и портом, состоянием сервиса и журналирования,
пулами DNS, bootstrap, выбранным режимом и VPN-подключением, группами доменов,
параметрами кэша и планировщика, фильтром AdGuard, собственными правилами
и исключениями.
Несохранённый черновик не входит в файл. Экспорт не меняет настройки сервиса;
кэш ответов, счётчики, журналы и приватные VPN-ключи в него не входят.
Тот же файл доступен по `GET /api/dnsserver/export`.

**«Импорт настроек»** сначала показывает содержимое файла, будущий адрес и порт
DNS, состояние сервиса и выбор VPN. Предварительный просмотр не сохраняет
настройки и не запускает сервис. После **«Применить импорт»** конфигурация из файла
заменяет все сохранённые параметры DNS и текущий черновик страницы. Размер файла
ограничен 16 МиБ. Настройки DNS на Keenetic и устройствах меняются отдельно.

Конкретный VPN сопоставляется по отпечатку публичных параметров подключения;
совпадение одного локального ID недостаточно. Если подходящего подключения нет
или совпадение неоднозначно, выберите замену. VPN-профили должны быть настроены
на целевом роутере заранее. Выключатели пар DoH и VPN переносятся вместе с
подтверждёнными подключениями; неподтверждённые пары пропускаются с предупреждением
в предварительном просмотре. Изменение настроек другим клиентом после просмотра
требует повторной проверки. При ошибке запуска импорт возвращает прежнюю
конфигурацию и показывает результат восстановления. Старые файлы версии 1 без
`scheduler_enabled` сохраняют включённый планировщик.

Экспорт, источники DNS-запросов, кэш и работа watchdog проверены на Keenetic ARM64.
Показатели CPU зависят от трафика, устройства и параметров VPN; оптимизации панели
не означают гарантированного ускорения отдельно установленного движка.

Статистика находится в начале страницы **DNS Server** и отдельным блоком на
**дашборде**: запросы, попадания в кэш, общие ответы, ответы через NFQWS/AWG, ошибки и заполнение
кэша. Кнопка **«Очистить кэш»** удаляет сохранённые DNS-ответы без перезапуска
сервиса и сброса счётчиков или рейтингов планировщика. Запросы, начатые до очистки,
могут ответить клиенту, но не сохранят свой результат в очищенный кэш.

**«Время хранения кэша, сек.»** задаёт верхний предел от 1 до 86400 секунд,
по умолчанию 3600. Если TTL провайдера меньше, запись истечёт раньше. Размер кэша
0 по-прежнему отключает хранение ответов.

Регистр имени не создаёт отдельную запись: `example.com` и `EXAMPLE.COM`
используют один кэш, а ответ сохраняет имя и идентификатор конкретного запроса.
A, AAAA, HTTPS и запросы с разными параметрами DNS имеют отдельные записи.
Ответы NXDOMAIN и ответы об отсутствии нужного типа записи сохраняются только
при наличии подходящей SOA, на срок не больше её TTL, SOA.MINIMUM и заданного
предела. Ошибки, усечённые ответы и ответы с нулевым TTL не кэшируются.

Одновременные одинаковые запросы могут получить результат одного обращения
к провайдеру: это **«Общий ответ»**, отдельно от **«Из кэша»**. Отмена одного
клиента не прерывает запрос остальных. Для повторно использованного ответа
провайдер и маршрут показываются в деталях как **«Первичный источник»**, а не
как новое обращение. Повторное сохранение тех же работающих настроек или
повторное включение DNS сохраняет кэш и счётчики.

Имена DoH-провайдеров разрешаются через независимые DoH bootstrap-запросы на том же
маршруте, без системного DNS роутера. Можно задать bootstrap IP вручную. Это исключает
DNS-петлю после переключения самого роутера на локальный сервер. AWG-правила получают
DNS-ответы и продолжают обучать IP-маршруты; фильтрация AAAA учитывает правила клиента.
Слушатели доступны только с выбранного LAN и loopback; выключение убирает собственные
правила firewall и маршруты сервиса.

## AmneziaWG

Настройки вкладки **«Маршрутизация»** общие для роутера. Добавление или выбор
подключения сохраняет режим, правила и открытый редактор. Основное и резервные
подключения выбираются в самом правиле; ключи и параметры туннелей остаются
отдельными для каждого подключения.

Переключатель **«Все поддомены»** внутри полного редактора матчей включает домен
и его поддомены, например `example.com`, `a.example.com` и `a.b.example.com`. Он работает и для
готовых `list:`/`geosite:` списков без изменения исходного файла. Выключение делает
обычные имена точными; сложные маски и регулярные выражения сохраняют явно заданный
смысл. Старые правила без сохранённого переключателя продолжают работать по прежним
правилам. Включение поддоменов включает DNS-обучение для такого правила.
До сохранения переключатель меняет только черновик правила.

Удаление подключения сохраняет связанные правила в состоянии **«Ожидает
подключения»**. Домены, IP, источники LAN, порядок, резервные подключения и настройка
поддоменов остаются в списке и сохраняются после перезапуска. Ожидающие правила не
участвуют в маршрутизации. Для возвращения правила в работу выберите VPN в его
редакторе. Удалённое резервное подключение сохраняется в списке резервов и может
быть заменено отдельно.

Кнопки **«Экспорт JSON»** и **«Импорт JSON»** переносят все правила. Экспорт включает
настройки и черновик, отображаемые на вкладке. Ссылки `list:`/`geosite:`/`geoip:`
заменяются содержимым списков только в файле экспорта, чтобы другой роутер не
зависел от локальных файлов; эти снимки не получают обновления исходных списков.
Если источник отсутствует или повреждён, экспорт сообщает об ошибке.

Каждое используемое подключение имеет короткий отпечаток публичных параметров
сервера, протокола и интерфейса. Импорт автоматически выбирает только единственное
точное совпадение. Одинаковое имя или локальный ID не подтверждает совпадение:
для изменённого или отсутствующего подключения выберите замену либо ожидание.
Приватные ключи и пароли в экспорт не входят; VPN-профили на другом роутере должны
быть настроены заранее. Адреса источников LAN переносятся без изменений.

Можно добавить правила в конец снимка текущей вкладки или заменить весь список
и общие настройки. Повтор того же добавления после потерянного ответа не создаёт
дубликаты. Изменение правил другим клиентом требует повторной проверки;
применение прежнего снимка после неё подтверждается отдельно. Размер файла
экспорта ограничен 2 МиБ.

Для ответов DNS, проходящих через перехват или встроенный DNS Server, маршрутизатор
добавляет подходящие адреса в правила до выдачи ответа устройству. Ошибка установки
даёт DNS-ошибку вместо адреса без подготовленного маршрута. При смене политики
панель показывает применение и результат. Уже открытые TCP/QUIC-соединения и DNS-кэш
приложения требуют переподключения; роутер не может назначить браузеру ошибку
`ERR_NETWORK_CHANGED`. Сторонний DoH/DoT на устройстве обходит DNS-обучение, а общие
CDN-адреса по-прежнему исключаются из правил на всю сеть, чтобы не изменить маршрут
других сайтов. Поэтому это не является гарантией маршрутизации любого трафика по
имени домена.

Если применение завершилось ошибкой, встроенный DNS-observer выдаёт SERVFAIL до
успешного восстановления маршрутов, чтобы не подтверждать адреса с неизвестным
маршрутом. Панель показывает причину. После ошибки восстановление повторно
проверяет ipset, маршруты, DNS-перехват и firewall, даже если файл hook сохранился.
На старом iptables Keenetic временная блокировка `iptables-restore` вызывает
ограниченный повтор; другие ошибки сразу возвращаются в панель. На Keenetic
проверено восстановление после ошибки применения и несколько сохранений подряд
при работающем DNS.

Ежеминутная проверка исправной политики читает состояние firewall, маршрутов и
наборов IP без их переустановки и без блокировки DNS-ответов. Если состояние
потеряно или предыдущая установка завершилась ошибкой, выполняется восстановление.
Плановое обновление неизменённых списков подготавливает отдельные наборы и
заменяет их через `ipset swap`, сохраняя изученные адреса и работающий DNS-перехват.
Обновление самой цепочки firewall сохраняет действующие переходы до применения
новой таблицы. Изменение настроек по-прежнему требует полного применения политики.

Подготовка списков AWG повторно использует уже известные IP и объединяет
одновременный прогрев одного имени, даже если домен встречается в нескольких
правилах. Неуспешный прогрев того же имени откладывается на минуту. Общий бюджет
подготовки — 30 секунд, отдельное разрешение имени ограничено 15 секундами;
системный resolver и резервный Go resolver разделяют этот срок. Go запрашивает
только недостающую семью адресов, если системный ответ уже содержит A или AAAA.
Это отдельные подсказки маршрутизации, которые не продлевают TTL DNS-ответов
устройствам и не запускают собственный периодический опрос доменов списка.

Маршрут самого DNS-запроса выбирается отдельно в **DNS Server**. Для Cloudflare
через туннель выберите **«Только VPN (AWG/WARP)»** и нужное подключение: сначала
запрос к провайдеру проходит через VPN, затем полученные адреса добавляются в
подходящее правило и ответ возвращается устройству.

Новые VPS-профили используют **AWG 3.1**. Переключатель **«Обфускация трафика»**
включает защиту заголовков, случайные дополнения пакетов, сигнатурные пакеты и
диапазоны таймеров. При выключении применяется формат WireGuard; шифрование
сохраняется. Параметры обфускации сохраняются для последующего включения.

Движок роутера и установщик VPS закреплены на официальных версиях
[amneziawg-go v3.1.20260828](https://github.com/amnezia-vpn/amneziawg-go/releases/tag/v3.1.20260828)
и [amneziawg-tools v3.1.20260812](https://github.com/amnezia-vpn/amneziawg-tools/releases/tag/v3.1.20260812).
Для VPS с AWG 3.1 используется userspace, чтобы старый модуль ядра не перехватил
создание интерфейса. Поддерживаются Debian/Ubuntu на amd64 и arm64.

Обновление движка сохраняет совместимость существующих AWG 1.x/2.0 и WARP.
Чтобы перевести свой VPS на новый формат, обновите движок в настройках
AmneziaWG, затем выберите **«Перейти на AWG 3.1» → «Сохранить и развернуть»**.
После успешного развёртывания заново импортируйте клиентские конфиги на остальных
устройствах с поддержкой AWG 3.1. WARP и импортированные подключения используют
формат своего сервера. Если развёртывание не завершилось, роутер сохраняет
последнюю применённую конфигурацию, в том числе после перезапуска панели.

Если на Keenetic/Entware установка движка из панели завершается сообщением
`скачивание движка: context deadline exceeded`, архив можно скачать работающим
на роутере `wget` и установить после проверки контрольной суммы:

```sh
mkdir -p /opt/tmp/awg2-install
cd /opt/tmp/awg2-install || exit 1
base=https://github.com/Omn1z/nfqws2-keenetic-strategy-selector/releases/latest/download
wget -O awg-engine-linux-arm64.tar.gz "$base/awg-engine-linux-arm64.tar.gz" || exit 1
wget -O awg-engine-linux-arm64.tar.gz.sha256 "$base/awg-engine-linux-arm64.tar.gz.sha256" || exit 1
sha256sum -c awg-engine-linux-arm64.tar.gz.sha256 || exit 1
tar -xzf awg-engine-linux-arm64.tar.gz amneziawg-go || exit 1
cp amneziawg-go /opt/usr/bin/amneziawg-go.new || exit 1
chmod 755 /opt/usr/bin/amneziawg-go.new || exit 1
mv -f /opt/usr/bin/amneziawg-go.new /opt/usr/bin/amneziawg-go || exit 1
```

Эти команды предназначены для ARM64; на другой архитектуре выберите соответствующий
файл релиза. После установки обновите страницу панели; при замене уже работающего
движка переподключите активные туннели. Если `wget` не может
получить архив, передайте архив и `.sha256` с компьютера по SCP в тот же каталог
и начните с проверки `sha256sum`.

Фоновая проверка охватывает все включённые туннели каждые 10 секунд. Если нет
свежего хендшейка и приёма данных в течение 5 минут, сначала отправляется
keepalive-проба. Без ответа за 90 секунд пересоздаётся только проблемный туннель.
При отсутствии интерфейса восстановление начинается сразу. Неудачные попытки
повторяются без ограничения количества, с паузой от 15 секунд до 5 минут;
создание интерфейса само по себе не считается восстановлением связи. Для WARP
повторяется подбор endpoint. Выключенные пользователем туннели не запускаются.

## Обновление

Повторите блок [установки](#установка) для своей платформы: единый `install.sh`
обновляет существующую панель и сохраняет конфиги, списки и выбранный порт.
Подготовку HTTPS-загрузчика можно повторять; скачивается последний стабильный релиз.
Для старого Keenetic ARM64 со сбоем `curl` используйте способ с локальным бинарником
из раздела установки. После обновления перезагрузите страницу веб-панели.

## Удаление

Скачайте скрипт подходящим загрузчиком. На OpenWrt после подготовки `curl`:

```sh
curl -4 -fL --connect-timeout 15 --max-time 180 \
  -o /tmp/n2s-uninstall.sh \
  'https://github.com/Omn1z/nfqws2-keenetic-strategy-selector/releases/latest/download/uninstall.sh' &&
sh /tmp/n2s-uninstall.sh
```

На Keenetic/Netcraze и других системах с Entware:

```sh
/opt/bin/wget -4 -T 30 -t 3 -O /tmp/n2s-uninstall.sh \
  'https://github.com/Omn1z/nfqws2-keenetic-strategy-selector/releases/latest/download/uninstall.sh' &&
sh /tmp/n2s-uninstall.sh
```

По умолчанию данные сохраняются. Для удаления вместе с данными замените последнюю
команду выбранного блока на `sh /tmp/n2s-uninstall.sh --purge`.

## Сборка из исходников

Нужны Go ≥ 1.26.0 (рекомендуется и используется в CI: 1.26.8) и Node 20.19+ или 22.12+ (веб-интерфейс — React 19 + TypeScript + Tailwind на
Vite). Скрипты сборки сами собирают фронтенд (`npm`) в один встраиваемый файл,
а затем линкуют бинарь.

```sh
sh scripts/build.sh v1.0.0        # Linux/macOS
powershell -File scripts/build.ps1 -Version v1.0.0   # Windows
```

Бинарники появятся в `dist/` для `arm64`, `arm` (v7), `mipsle`, `mips` и `amd64` (x86_64 OpenWrt).

Движок AmneziaWG собирается отдельно с Go 1.26.8:

```sh
sh scripts/build-engine.sh
powershell -File scripts/build-engine.ps1 -Go /path/to/go.exe
```

Архивы `awg-engine-linux-<arch>.tar.gz` и обязательные SHA256-файлы появляются
в `dist/`. Установщик проверяет контрольную сумму, архитектуру и поддержку 3.1
до замены существующего движка.

Исходники движка закреплены на AmneziaWG `v3.1.20260828`; зависимости для сборки
роутера и userspace-движка на VPS зафиксированы отдельно в
`internal/services/awg/engine-deps.mod` и `engine-deps.sum`. Они применяются через
`-modfile`, без изменения upstream-кода протокола. При обновлении панели уже
установленный движок заменяется отдельно кнопкой «Обновить движок».

В CI релиз блокируется при найденных уязвимостях используемого Go-кода
(`govulncheck`) или зависимостей интерфейса (`npm audit`). Проверка движка использует
сборки с сохранёнными символами для всех четырёх архитектур. Для такой же проверки
локально задайте `GOVULNCHECK` — путь к исполняемому файлу `govulncheck`.

## Поддерживаемые архитектуры

`aarch64` (arm64), `armv7` (arm), `mipsel` (mipsle), `mips`, `x86_64` (amd64). На
Entware и OpenWrt с `opkg` установщик читает архитектуру из `opkg
print-architecture`; на OpenWrt 25.12+ — из `apk --print-arch`. Для MIPS
порядок байтов определяется по ELF, поэтому big-endian устройства получают
бинарь `mips`, а little-endian — `mipsle`.
