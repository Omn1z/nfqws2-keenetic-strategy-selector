# NFQWS2 Strategy Selector для Keenetic

Веб‑инструмент для **автоматического подбора рабочих стратегий обхода DPI** для
[`nfqws2-keenetic`](https://github.com/Anonym-tsk/nfqws-keenetic) (движок
[zapret2](https://github.com/bol-van/zapret2), Lua). Запускается прямо на роутере,
тестирует стратегии в несколько потоков на ваших списках доменов/IP, сохраняет
только те, что реально работают (есть ответ и нет обрыва на 16 КБ), и сортирует
их по скорости.

> ⚠️ Требуется уже установленный пакет **`nfqws2-keenetic`** (бинарь
> `/opt/usr/bin/nfqws2`, движок zapret2 v0.9.x) и Entware с `iptables`.

## Возможности

- **Веб‑интерфейс** — один статический бинарник со встроенным UI, без зависимостей.
- **Дашборд и мониторинг** — главная страница со сводкой (статистика TG WS Proxy,
  активные соединения, пакеты DPI‑движка очереди NFQUEUE, трафик WAN) и **живыми
  графиками нагрузки**; вкладка «Соединения» (живой conntrack с фильтром и
  сортировкой) и «Активность устройств» — что устройства LAN не могут открыть
  (кандидаты на подбор стратегий, отправляются в прогон одной кнопкой). Для отладки
  соединений у каждого устройства — **трассировка 30 с** (таймлайн conntrack) и
  **захват пакетов `.pcap`** (`tcpdump`, ставится по запросу), открываемый в Wireshark.
- **Логи** — живой просмотр логов сервиса по модулям (включая TG WS Proxy), с
  фильтром, паузой и авто‑прокруткой.
- **Система** — настройка портов веб-панели и DNS-сервера, отключение авторизации
  (с подтверждением) и логирования.
- **Списки** доменов и IP/CIDR; к каждому списку прикрепляются найденные ранее
  рабочие («базовые») стратегии.
- **Прогоны в несколько потоков** — выбираете число потоков, стратегии тестируются
  параллельно (каждый поток — изолированная песочница).
- **Изоляция трафика** — основной сервис nfqws2 продолжает работать, тестовый
  трафик отводится отдельными правилами iptables (сеть не нарушается во время прогона).
- **Метрики и сортировка** — задержка (TTFB), пропускная способность (КБ/с) и
  комбинированный «коэффициент скорости»; таблица сортируется по любой колонке.
- **Свои блобы** — загрузка собственного fake‑payload, **создание `ClientHello`**
  (снять с трафика устройства через `tcpdump` или сгенерировать по домену) и
  **корзина** (удаление в корзину с восстановлением).
- **Применение** найденной стратегии в основной конфиг nfqws2 (с резервной копией).
- **Авторизация** по логину/паролю роутера (как в nfqws-keenetic-web). Отключение — `N2S_NOAUTH=1`.
- **Выбор блобов для прогона** — отмеченные блобы загружаются во все тестируемые стратегии.
- **GeoSite/GeoIP** — загрузка `geosite.dat`/`geoip.dat` или текстового списка и импорт категории в тестовый список.
- **DNS (DoH/DoT)** — список шифрованных DNS (Google, Cloudflare, Comss, Yandex,
  xbox-dns, GeoHide, AdGuard и свои). В прогоне можно прогнать стратегии через
  каждый выбранный DNS — в результатах видно, какой DNS открыл доступ.
- **Telegram-прокси** (вкладка «Telegram», подвкладки **MT Proto** и **SOCKS5**) —
  два взаимозаменяемых прокси прямо на роутере: **MTProto → WebSocket** и **SOCKS5**
  (на базе TGLock). Оба туннелируют трафик Telegram по WSS к `web.telegram.org`
  (обход блокировки по IP); по умолчанию выключены. SOCKS5 опционально защищается
  логином/паролем. MTProto-компонент синхронизирован с **Flowseal TG WS Proxy
  v1.10.2**: восстановление слушающего порта и пула WS, несколько CF/Worker-доменов,
  ежечасное обновление резервных доменов и поддержка тестовых DC. Старые секреты,
  порты и DC-редиректы сохраняются. [Ревизия и границы переноса](internal/services/tgws/UPSTREAM.md).
- **Управление движком NFQWS2** (вкладка «Сервисы → NFQWS2») — редактирование
  конфига (`nfqws2.conf`: быстрые настройки + полный текстовый редактор),
  Lua‑скриптов обхода и списков доменов/IP прямо в панели (загрузка/скачивание/
  удаление, дедуп списков, защита критичных файлов). Показ версии движка рядом с
  версией пакета и обновление движка по `opkg` при наличии нового релиза.
  «Применить (reload)» по `SIGHUP` перечитывает списки без обрыва очереди.
  Полноценная замена стороннего `nfqws-keenetic-web`.
- **Установщик / обновление / удаление**, мульти‑арч сборки в GitHub Releases.
- **AmneziaWG 3.1** — развёртывание VPS по SSH, импорт AWG/WireGuard/WARP,
  несколько туннелей, правила маршрутизации и автовосстановление соединений.

## Установка

```sh
curl -fsSL https://raw.githubusercontent.com/Omn1z/nfqws2-keenetic-strategy-selector/v1.6.0/packaging/install.sh | sh
```

После установки откройте `http://<IP‑роутера>:8090`.

Сервис ставится как `/opt/etc/init.d/S52nfqws2-strategy` (автостарт), данные — в
`/opt/etc/nfqws2-strategy/`.

## Использование

1. **Списки** → создайте список, вставьте домены (по одному в строке), сохраните.
2. **Прогон** → задайте число потоков, при желании выберите конкретные стратегии
   (по умолчанию — все), нажмите «Запустить». Прогресс и результаты обновляются вживую.
3. **Результаты** → таблица сортируется по задержке / скорости / коэффициенту.
   Рабочие стратегии (зелёные, прошли все цели) автоматически сохраняются в список.
4. **Применить** → понравившуюся стратегию можно записать в `nfqws2.conf`
   (создаётся бэкап `*.n2s.bak`) и при желании перезапустить сервис.
5. **Блобы** → вкладка для загрузки своих fake‑payload; путь подставляется в
   стратегию как `--blob=имя:@/путь`.

## Как это работает

Каждый поток («песочница») получает отдельный номер очереди NFQUEUE, диапазон
исходных портов и временные цепочки iptables. Тестовые соединения помечаются
connmark `0x20000000`, поэтому основной nfqws2 (очередь 300) их игнорирует, а
тестовый экземпляр nfqws2 с проверяемой стратегией обрабатывает только их.
HTTP‑клиент скачивает тестовый URL через песочницу, измеряет байты/время и ловит
обрыв на ~16 КБ. По завершении все правила и процессы убираются.

## DNS Server

Отдельный локальный DNS-сервис в меню **«Сервисы → DNS Server»**. По умолчанию
выключен. Его включение не меняет DNS роутера или устройств: клиентские настройки
переключаются отдельно, когда вы готовы.

Для LAN-адреса `192.168.3.1` адрес подключения по умолчанию:

| Протокол | Адрес |
| --- | --- |
| Обычный DNS, UDP и TCP | `192.168.3.1:5355` |

Адрес LAN определяется автоматически. Укажите IP и порт в настройках **обычного
DNS** клиента. Локальный сервис принимает DNS по UDP и TCP без TLS: установка
сертификатов не нужна, локальных DoH/DoT/DoQ-адресов нет.

Порт DNS и порт веб-панели меняются в **«Система → Порты»**. По умолчанию панель
использует порт `8090`, DNS-сервис — `5355`. Порт `53` обычно занят встроенным DNS
роутера. Если устройство принимает только IP без порта, оно использует `53`:
настройте DNS роутера на локальный сервис с портом `5355` либо выберите свободный
порт `53` для сервиса. Настройка клиента должна соответствовать выбранному порту.
Порты применяются после сохранения; при смене порта панели интерфейс открывает
новый адрес. Сохранение порта DNS не включает выключенный сервис.

В блоке **«Специальные DoH и домены»** сначала выбирается DoH-сервер или пул,
затем ему назначается один домен или список: по строкам, через запятую или точку
с запятой. По умолчанию одна группа объединяет `claude.com`, `claude.ai`, `grok.com`
и их поддомены под `https://xbox-dns.ru/dns-query`. Существующие правила с одинаковым
пулом и настройками автоматически отображаются одной группой. Включение группы
и обработка поддоменов настраиваются сразу для всего списка.
Остальные имена используют настраиваемый пул по умолчанию. В каждом пуле может
быть до восьми DoH-серверов: их можно добавить вручную или выбрать несколько
из существующего списка на вкладке «DNS». Домены группы используют только
её пул, без подмешивания серверов из общего пула. Побеждает самое точное
совпадение домена; выключенные группы пропускаются. Передаются все обычные типы
DNS-записей, включая A, AAAA и HTTPS; положительные ответы кэшируются по TTL.
От роутера к выбранному DoH-провайдеру запросы идут по HTTPS с проверкой
подлинности его сертификата.

Запрос без ответа в кэше одновременно направляется к провайдерам подходящего
пула через NFQWS и выбранные AWG-подключения. В режиме **«Авто»** участвуют все доступные включённые туннели,
включая WARP. Первый успешный ответ сразу возвращается клиенту, оставшиеся попытки
отменяются. Медленный или заблокированный маршрут не задерживает ответ другого
маршрута. Каждый новый запрос снова пробует все выбранные маршруты; таймаут
ограничивает каждую попытку отдельно.

Можно выбрать конкретный AWG для параллельного запроса вместе с NFQWS или
**«Выключено — только NFQWS»**. Каждая пара «DoH-сервер + маршрут» участвует
отдельно. Корректный ответ NXDOMAIN тоже считается ответом DNS; таймауты,
ошибки HTTPS, SERVFAIL и REFUSED не могут выиграть гонку. Кэшированный ответ
возвращается без новых сетевых запросов. Текущая интеграция NFQWS обрабатывает DoH
на HTTPS-порту 443; для нестандартного порта используются выбранные AWG-подключения.

Настройка **fast-dns** включена по умолчанию: IP-адреса DoH-серверов заранее
загружаются в память и обновляются в фоне раз в час. Одновременные запросы одного
адреса используют общий результат; прогрев выполняют не более двух работников.
При ошибке обновления последний известный IP доступен ещё до часа, а повторная
попытка выполняется через минуту. Ошибка подключения также запускает обновление
с защитой от частых повторов. Адреса учитываются отдельно для каждого маршрута;
вручную заданные IP и DoH с IP в URL имеют приоритет. Кэш ограничен 256 записями
«имя DoH + маршрут», по 16 IP в каждой, и не изменяет проверку сертификатов HTTPS.
Перезапуск сервиса запускает новый прогрев. При выключенном fast-dns работает
обычный кэш bootstrap по TTL, максимум пять минут. Кэш ответов для устройств
и его кнопка очистки на эти адреса не влияют.

Блок **«Планировщик»** по умолчанию показывает общий пул DNS. В режиме
**«По домену»** можно посмотреть очередь для конкретного имени. Для каждого
варианта показаны DoH-провайдер, маршрут, задержка успешных ответов, надёжность,
ошибки и составляющие оценки.
Чем больше очков, тем раньше вариант получает свободный слот. Оценка равна
`100 × надёжность − min(80, задержка / 20) − min(100, 20 × ошибок подряд)`.
Первый завершённый замер задаёт фактическую надёжность и задержку; следующие
сглаживаются по правилу 80/20. Ошибки снижают приоритет, отмена после победы
другого варианта не считается ошибкой и не обновляет время последнего замера.
Раз в пять секунд планировщик выбирает один вариант для независимой фоновой
проверки: сначала без результата, затем с самым старым замером (от минуты).
Такая проверка доводится до ответа или таймаута, даже если клиент уже получил
ответ другого сервера. Она занимает один из общих 32 слотов и пропускается,
когда они заняты. Поэтому быстрый вариант из конца очереди может снова стать
лидером. После пяти минут без результата устаревшая оценка заменяется новым
измерением. Фоновые запросы не заполняют кэш ответов, статистику клиентов или
AWG-маршрутизацию: общий пул проверяется вопросом NS корневой зоны, специальные
пулы — доменом из своей группы. В таблице видны время последнего результата,
состояние и счётчики фоновых проверок. Оценки сохраняются при изменении настроек
DNS; после перезапуска панели варианты измеряются заново.

**«Журнал DNS»** показывает ответы, кэш, отмены и ошибки. Логирование
включено по умолчанию и переключается отдельно, без перезапуска DNS. Журнал
хранится только в памяти; сериализованные записи занимают не более 128 КиБ, старые
записи удаляются при добавлении новых. Доступны пауза просмотра, фильтр и очистка.
Отменённые попытки одного запроса объединяются в одну запись со счётчиком;
успешный ответ не дублируется отдельной записью успешного маршрута. Короткие
строки и значки заменяют повторяющиеся пояснения, соседние отмены показываются
рядом со своими доменами. Ошибки сохраняют причину, а подробности запроса доступны
в раскрывающейся строке. Отмены не ухудшают оценки планировщика и не задерживают
возврат первого ответа.
Перезапуск панели очищает журнал, а перезапуск одного DNS-сервиса сохраняет его.

Статистика находится в начале страницы **DNS Server** и отдельным блоком на
**дашборде**: запросы, попадания в кэш, ответы через NFQWS/AWG, ошибки и заполнение
кэша. Кнопка **«Очистить кэш»** удаляет сохранённые DNS-ответы без перезапуска
сервиса и сброса счётчиков или рейтингов планировщика. Запросы, начатые до очистки,
могут ответить клиенту, но не сохранят свой результат в очищенный кэш.

**«Время хранения кэша, сек.»** задаёт верхний предел от 1 до 86400 секунд,
по умолчанию 3600. Если TTL провайдера меньше, запись истечёт раньше. Размер кэша
0 по-прежнему отключает хранение ответов.

Имена DoH-провайдеров разрешаются через независимые DoH bootstrap-запросы на том же
маршруте, без системного DNS роутера. Можно задать bootstrap IP вручную. Это исключает
DNS-петлю после переключения самого роутера на локальный сервер. AWG-правила получают
DNS-ответы и продолжают обучать IP-маршруты; фильтрация AAAA учитывает правила клиента.
Слушатели доступны только с выбранного LAN и loopback; выключение убирает собственные
правила firewall и маршруты сервиса.

## AmneziaWG

Новые VPS-профили используют **AWG 3.1**. Переключатель **«Обфускация трафика»**
включает защиту заголовков, случайные дополнения пакетов, сигнатурные пакеты и
диапазоны таймеров. При выключении применяется формат WireGuard; шифрование
сохраняется. Параметры обфускации сохраняются для последующего включения.

Движок роутера и установщик VPS закреплены на официальных версиях
[amneziawg-go v3.1.20260828](https://github.com/amnezia-vpn/amneziawg-go/releases/tag/v3.1.20260828)
и [amneziawg-tools v3.1.20260812](https://github.com/amnezia-vpn/amneziawg-tools/releases/tag/v3.1.20260812).
Для VPS с AWG 3.1 используется userspace, чтобы старый модуль ядра не перехватил
создание интерфейса. Поддерживаются Debian/Ubuntu на amd64 и arm64.

Обновление движка сохраняет совместимость существующих AWG 1.x/2.0 и WARP.
Чтобы перевести свой VPS на новый формат, обновите движок в настройках
AmneziaWG, затем выберите **«Перейти на AWG 3.1» → «Сохранить и развернуть»**.
После успешного развёртывания заново импортируйте клиентские конфиги на остальных
устройствах с поддержкой AWG 3.1. WARP и импортированные подключения используют
формат своего сервера. Если развёртывание не завершилось, роутер сохраняет
последнюю применённую конфигурацию, в том числе после перезапуска панели.

Фоновая проверка охватывает все включённые туннели каждые 10 секунд. Если нет
свежего хендшейка и приёма данных в течение 5 минут, сначала отправляется
keepalive-проба. Без ответа за 90 секунд пересоздаётся только проблемный туннель.
При отсутствии интерфейса восстановление начинается сразу. Неудачные попытки
повторяются без ограничения количества, с паузой от 15 секунд до 5 минут;
создание интерфейса само по себе не считается восстановлением связи. Для WARP
повторяется подбор endpoint. Выключенные пользователем туннели не запускаются.

## Сборка из исходников

Нужны Go ≥ 1.25.0 (CI: 1.25.7) и Node 20.19+ или 22.12+ (веб-интерфейс — React 19 + TypeScript + Tailwind на
Vite). Скрипты сборки сами собирают фронтенд (`npm`) в один встраиваемый файл,
а затем линкуют бинарь.

```sh
sh scripts/build.sh v1.0.0        # Linux/macOS
powershell -File scripts/build.ps1 -Version v1.0.0   # Windows
```

Бинарники появятся в `dist/` для `arm64`, `arm` (v7), `mipsle`, `mips`.

Движок AmneziaWG собирается отдельно с Go 1.25.7:

```sh
sh scripts/build-engine.sh
powershell -File scripts/build-engine.ps1 -Go /path/to/go.exe
```

Архивы `awg-engine-linux-<arch>.tar.gz` и обязательные SHA256-файлы появляются
в `dist/`. Установщик проверяет контрольную сумму, архитектуру и поддержку 3.1
до замены существующего движка.

## Поддерживаемые архитектуры

`aarch64` (arm64), `armv7` (arm), `mipsel` (mipsle), `mips`. Установщик определяет
архитектуру через `opkg print-architecture`.
