## [v1.7.2] — 2026-10-04

Автоматическое подключение DNS Server к OpenWrt, перенос DNS-настроек между
роутерами и обнаружение DNS провайдера на чистых установках Keenetic.

### DNS Server: импорт на другой роутер

- При отсутствии исходного Amnezia-подключения импорт предлагает режим «Автоматически» и доступные подключения нового устройства. Перенос больше не блокируется из-за несовпадающих идентификаторов VPN или отсутствия настроенных туннелей.
- Автоматическое сопоставление учитывает отпечаток подключения; одинаковое имя или идентификатор другого сервера не считаются совпадением. Выбранная вручную замена повторно проверяется перед применением.
- Режим «Только VPN» сохраняется: импорт с автоматическим выбором не разрешает скрытый переход DNS-запросов напрямую. Если подходящего VPN пока нет, настройки можно перенести заранее.
- Недоступный LAN-адрес из исходного JSON адаптируется к адресу нового роутера с пояснением в предварительной проверке. Проверка собственного upstream, занятых портов, конкурирующих изменений и восстановление предыдущих настроек при неудачном запуске сохраняются.

### Shadow DNS: чистые установки Keenetic

- Исправлен запуск штатного `ndmc` из Entware: только дочерняя команда использует библиотеки KeeneticOS вместо несовместимых библиотек Entware. Это устраняет подтверждённый случай `ndmc: initialization failure`, из-за которого Shadow DNS не мог прочитать данные провайдера.
- Ошибки чтения KeeneticOS больше не маскируются сообщением об ожидании DHCP/PPP. Диагностика отличает текущий сбой команды от старой записи в системном журнале и не раскрывает содержимое журнала.
- Когда журнал уже не содержит DHCP-аренду и адрес DHCP-сервера неизвестен, добавлено начальное обнаружение через DHCPINFORM. Оно разрешено только на проверенном физическом WAN с действующим адресом и основным маршрутом; LAN и VPN не используются для такого запроса.
- Обнаружение запрашивает только параметры DNS, не меняет IP или аренду, не перезапускает WAN и не занимает UDP-порт штатного DHCP-клиента. Адрес шлюза не подставляется вместо адреса DNS-сервера.
- Ответы проверяются по интерфейсу, IP, MAC, случайному идентификатору транзакции и идентификатору DHCP-сервера. Пакеты постороннего UDP-трафика отсеиваются фильтром сокета; ожидание и частота повторных попыток ограничены. Успешные ответы кэшируются, а внутренний тайм-аут не запускает повторное обнаружение на каждом DNS-запросе.
- Проверенный DHCP-сервер сохраняется для последующих запросов с повторной проверкой текущего WAN. Это не создаёт фиктивную аренду DNS и не переносит сведения между загрузками устройства.

### OpenWrt 24/25+: автоматическое подключение DNS Server

- В разделе DNS Server добавлена карточка «DNS OpenWrt»: выбор интерфейса и экземпляра dnsmasq, применение и восстановление прежнего DNS. На Keenetic используется прежняя инструкция подключения.
- Кнопка «Подключить DNS Server» задаёт `Use custom DNS servers` выбранного интерфейса и отключает автоматический DNS этого интерфейса. Поскольку UCI принимает здесь только IP, выбранный dnsmasq дополнительно направляется на фактический IP и порт локального DNS Server. Перед изменениями проверяются ответы UDP и TCP работающего сервиса.
- Обычные upstream выбранного dnsmasq заменяются локальным сервисом; специальные правила для отдельных доменов сохраняются. Изменение действует на все сети этого экземпляра dnsmasq. Shadow DNS продолжает получать адреса провайдера из данных OpenWrt, включая `inactive.dns-server`.
- Сохраняется резервная копия четырёх изменяемых параметров, включая отсутствующие значения и списки. Проверяются актуальность просмотренной конфигурации, обнаруженные несохранённые UCI-изменения и конфликты с внешними изменениями. Операции панели и команды восстановления сериализуются, при ошибке выполняется попытка отката; незавершённая операция сохраняет данные для восстановления.
- Поддерживаются именованные и анонимные экземпляры dnsmasq: изменение внутреннего `cfg…`-идентификатора после сохранения не теряет привязку. Неоднозначность или перестановка экземпляров останавливает автоматическую перезапись.
- Перед отключением DNS Server, сменой его адреса/порта или удалением панели восстанавливаются прежние настройки OpenWrt. Конфликт останавливает операцию, сохраняя резервную копию. Перезапуск и обновление с прежним адресом сохраняют привязку; после смены адреса подключение применяется заново.
- Клиентские DNS-настройки вручную не перехватываются. Внешние конфиги dnsmasq могут задавать дополнительные upstream и показываются как предупреждение. Одновременное изменение этих параметров в LuCI/SSH и панели не поддерживается; перечитывание конфигурации dnsmasq может вызвать короткую паузу DNS.

### Установка и обновление

- Опубликован официальный установщик на GitHub Pages: скрипт и бинарники панели загружаются с `omn1z.github.io` без перехода на `release-assets.githubusercontent.com`. Он автоматически определяет платформу и архитектуру, проверяет SHA-256 файлов и передаёт проверенный бинарник обычному установщику.
- В инструкции добавлена общая команда с подготовкой HTTPS-загрузчика для Keenetic/Entware и OpenWrt с opkg или apk. Раздельные инструкции для OpenWrt до 24.10 и 25+ сохранены.
- Публикация установщика синхронизируется с завершённым стабильным релизом; предыдущий стабильный выпуск сохраняется для уже скачанных установочных скриптов. Проверка TLS остаётся включённой.

## [v1.7.1] — 2026-10-03

Исправления автоподбора NFQWS2, маршрутизации AWG и автоматического определения
DNS провайдера. Добавлен раздел ARP Block для штатной изоляции Wi-Fi клиентов Keenetic.

### NFQWS2: защита HTTPS при автоподборе

- Исправлен случай, когда автоподбор заменял рабочую стратегию TLS/443 на профиль только для HTTP/80. После такой замены новые HTTPS-соединения могли завершаться ошибками или тайм-аутами, хотя уже открытые соединения и QUIC продолжали работать.
- Текущая проверка использует HTTPS по IPv4/TCP/443 и теперь отбирает совместимые стратегии по фактическим аргументам, а не подписи протокола. Учитываются фильтры портов, IPv4, TLS и payload отдельных Lua-инструкций; HTTP/QUIC-профили не получают ложный успешный результат этой проверки.
- Перед автоматическим применением повторно проверяются аргументы победителя и успешность всех целей. Отменённый или ошибочный запуск не применяется; неподходящий результат отклоняется до изменения конфига и резервной копии. Чтение результатов использует согласованный снимок состояния.
- Ручное применение HTTP-стратегий и редактирование конфига остаются доступны. Это исправление совместимости профилей с HTTPS-проверкой, а не добавление отдельных тестов HTTP и QUIC.

### AWG: домены на общих CDN-адресах

- Явное правило VPN теперь направляет домен через выбранный туннель и тогда, когда DNS возвращает общий адрес CDN. Ранее такой адрес мог быть пропущен защитой общих CDN и сайт продолжал открываться напрямую, несмотря на правило AWG.
- Исправление применяется к подготовке списков, DNS-обучению и обработке SNI; установка адреса в маршрут по-прежнему завершается до выдачи DNS-ответа клиенту. Защита от глобальных прямых исключений для общих CDN сохраняется.
- Маршрутизация остаётся основанной на IP: другие домены на том же точном IP могут попасть в то же правило. Целая сеть CDN автоматически в VPN не добавляется.

### Shadow DNS: восстановление DNS провайдера на Keenetic

- Неполная запись DHCP-обновления без списка DNS больше не удаляет ранее полученные адреса, пока действует их подтверждённый срок. Срок старых данных не продлевается искусственно; смена WAN, адреса, загрузки устройства или истечение аренды учитываются отдельно.
- Если штатные данные Keenetic не содержат DNS, добавлен запрос DHCPINFORM к ранее определённому DHCP-серверу активного WAN. Он запрашивает только параметры DNS, не обновляет и не освобождает аренду, не меняет адрес интерфейса и не занимает UDP-порт штатного DHCP-клиента.
- Ответ проверяется по серверу, интерфейсу, адресу клиента, MAC и идентификатору транзакции. Ожидание ограничено 1,2 секунды; успешные ответы кэшируются, а повторные неудачные попытки имеют паузу, чтобы не создавать постоянные запросы.
- Автоматический выбор сохраняется без ручного поля DNS и без скрытой подстановки публичного резолвера. OpenWrt продолжает получать параметры DNS через штатные данные ubus.

### ARP Block

- В разделе «Сервисы» появился ARP Block: просмотр сегментов, SSID и подключённых Wi-Fi клиентов, включение штатной `peer-isolation` Keenetic для выбранного сегмента.
- Изменение требует подтверждения, проверяет актуальность конфигурации и результат применения. При ошибке сохранения выполняется попытка отката. Запуск панели сам по себе не меняет изоляцию; обработка пакетов остаётся у Keenetic.
- Возможность действует на всех Wi-Fi клиентов выбранного сегмента. Индивидуальные MAC-исключения, изоляция проводных клиентов между собой и запрет доступа к DNS/службам самого роутера в эту реализацию не входят. Это не гарантия полного сокрытия устройств в общей сети.
- На OpenWrt раздел сообщает об отсутствии управления изоляцией из панели и направляет к настройке изолированной сети в LuCI.

### Проверки и обновление

- Добавлены регрессионные тесты несовместимых стратегий и защиты автоприменения, общих CDN, сохранения DHCP-данных и разбора/отмены DHCPINFORM, а также сервиса, API и состояния интерфейса ARP Block.
- На Keenetic ARM64 проверены восстановление HTTPS YouTube, маршрутизация сайта через AWG и автоматическое получение DNS. Новые изменения OpenWrt проверяются платформенными тестами и сборками; живой OpenWrt в этой серии проверок не использовался.
- Обновление сохраняет настройки и правила. После установки перезагрузите открытую страницу панели для загрузки нового интерфейса. Если прежний автоподбор уже сохранил неподходящую стратегию, обновление не угадывает её замену: восстановите свою рабочую стратегию либо запустите подбор заново.

## [v1.7.0] — 2026-10-03

Новый редактор и проводник стратегий NFQWS2, тема shadcn Neutral / Rhea,
Shadow DNS, перенос настроек DNS и правил AWG, исправления кэша, маршрутизации
и ARP на Keenetic. Ниже перечислены изменения после v1.6.16.

### Интерфейс и редактор NFQWS2

- Светлая и тёмная темы используют палитру shadcn **Neutral**, стиль **Rhea**, шрифт **Inter** для текста и заголовков и малые скругления. Обновлены общие кнопки, поля, переключатели, диалоги, карточки и таблицы; интерактивные компоненты используют Base UI. Inter включён в сборку и не требует обращения к серверу шрифтов.
- Выпадающие списки во всех разделах переведены на общий Select на Base UI в стиле shadcn Rhea, включая ранее отдельные нативные списки. Общие Switch приведены к размерам Rhea; исправлены доступные имена, фокус и отображение ошибок. Изменения распространяются на весь интерфейс, а не только на настройки NFQWS2.
- Автоматика NFQWS2 вынесена в отдельную вкладку. Структурированный редактор содержит параметры запуска, базовую стратегию HTTP(S), стратегии QUIC и UDP, пользовательскую стратегию, IPSET и режим работы. Неизвестные параметры, комментарии и дополнительные аргументы сохраняются; сложные shell-конструкции остаются доступны в полном конфиге.
- Режим работы переключается тремя видимыми кнопками **`auto` / `list` / `all`** вместо выпадающего списка, по образцу nfqws-keenetic-web. Выбор доступен с клавиатуры и сохраняет остальные аргументы настройки; пользовательский режим помечается отдельно.
- CodeMirror добавляет подсветку Shell и Lua, поиск на русском языке, историю отмены, сочетание клавиш для сохранения и проверку скобок. Смена темы сохраняет черновик и историю правок.
- Для отдельных блоков стратегий добавлен разбор аргументов NFQWS: флаги, числа, переменные, пути, Lua-функции и их параметры выделяются отдельно, включая многострочные значения внутри кавычек полного `nfqws2.conf`. Палитра основана на цветах VS Code, используемых в nfqws-keenetic-web, с сохранением нейтрального фона интерфейса; подсветка согласована между полным конфигом и фрагментами стратегий.
- В `TCP_PORTS` и `UDP_PORTS` отдельно подсвечиваются все номера портов, запятые и границы диапазонов через `:` — в значениях с кавычками и без них.
- Подсказки редактора проверяют литеральные пути к конфигам, спискам, блобам и Lua на роутере. Исправление доступно для одного пути при наведении или сразу для всего файла; учитываются `/opt/etc/nfqws2` на Keenetic и `/etc/nfqws2` на OpenWrt. Подстановки shell/Lua не исполняются и не переписываются.

### File Explorer и архивы стратегий

- Проводник показывает дерево папок, вложенные каталоги и навигационную цепочку для конфигов, списков, блобов, Lua и shell-скриптов. Поиск работает внутри выбранной папки; переход между папками сохраняет открытый черновик.
- В проводнике и редакторе списков файлы разделены на «Текущие» и «Оригинальные» (`.list-opkg`, включая сжатые копии). Категории не меняют пути файлов; поиск и счётчики учитывают выбранную категорию, а открытый черновик сохраняется при переключении.
- Кнопка «Дедуп поддоменов» в редакторе списков удаляет обычные записи, уже покрытые родительским доменом в том же списке, без добавления новых доменов. Сохраняются точные правила `^`, комментарии, порядок и формат оставшихся строк; учитывается первое вхождение домена, определяющее режим NFQWS2. Изменяется только черновик до нажатия «Сохранить»; операция отдельно отменяется через «Отменить» или Ctrl+Z. Неоднозначный формат и слишком длинные строки оставляются без изменений с предупреждением.
- Drag & Drop загружает файлы и папки с сохранением вложенной структуры в допустимых каталогах; доступны обычный выбор файлов и выбор папки. Существующий файл заменяется только после подтверждения.
- Меню по правой кнопке мыши и кнопка **`···`** дают доступ к открытию, скачиванию и удалению файла. Удаление требует подтверждения; действующий основной конфиг защищён от удаления. Меню доступно также с клавиатуры и на мобильном экране.
- В таблице отображается время изменения файлов и папок из файловой системы роутера, в часовом поясе браузера; подсказка показывает секунды и зону. Для папки это время изменения самого каталога, а не самого нового вложенного файла. На узких экранах дата остаётся под именем.
- Редактор защищает несохранённые изменения при открытии другого файла и предупреждает, если файл поменялся после загрузки. Поздний ответ на старый запрос не заменяет уже открытый файл.
- ZIP-экспорт стратегии включает `nfqws2.conf`, `lists/`, `blobs/`, `lua/` и `scripts/`. Импорт поддерживает как полный архив, так и один конфиг, показывает предварительный просмотр и требует выбрать, сохранить свои userlist/autolist или применить входящие.
- Перед импортом создаётся резервный архив. Именованные снимки позволяют сохранить текущую стратегию перед экспериментом, скачать её и восстановить позже. Ошибка импорта вызывает откат; изменения файлов после предварительного просмотра требуют повторной проверки.
- Архивы и загрузки проверяются на допустимые пути, размер и тип файлов; выход за управляемые каталоги и обход через символические ссылки запрещены. Блобы и gzip сохраняются побайтно, для текстовых конфигов и списков нормализуются окончания строк Windows. Импорт скриптов не запускает их и не перезапускает NFQWS автоматически.

### Версии NFQWS2 и NFQUEUE bypass

- Версия пакета `nfqws2-keenetic` из `opkg`/`apk` и версия движка zapret2 теперь всегда остаются раздельными. Таймаут или ошибка чтения базы пакетов показывает неизвестное состояние и не подменяет версию пакета версией движка, устраняя ложное предложение обновления.
- Сравнение обновлений учитывает ревизии пакетов `-1` и `-r0`; установленная новая версия не предлагается к понижению. Отдельно различаются отсутствующий пакет, ошибка определения и вручную установленный движок.
- NFQUEUE bypass использует два поиска по `ipset hash:net` вместо двух правил на каждый IP. Сохраняются IPv4/IPv6, оба направления, CIDR и семантика `ACCEPT`; большие списки больше не требуют линейного обхода сотен правил.
- Адреса bypass готовятся отдельно, обновления панели и firewall hooks сериализуются, а ошибка заполнения или применения сохраняет предыдущую политику. Без поддержки ipset остаётся пакетная загрузка обычных правил; отсутствие или отказ `iptables-restore` не очищает работающую цепочку.

### DNS Server и Shadow DNS

- **Shadow DNS** направляет выбранные домены напрямую к DNS активного WAN. Правила — обычный список масок, например `*.ru`, `*.рф`, `*.vk.*`, `*.avito.*`; начальное `*.` включает сам домен и его поддомены, остальные звёздочки соответствуют одной целой DNS-метке. Поддерживаются кириллические домены.
- DNS для Shadow определяется автоматически через KeeneticOS или `ubus` OpenWrt 24/25+, включая доступные сведения DHCP. Ручного ввода адресов нет; старые ручные адреса игнорируются. Изученные сведения DHCP сохраняются с привязкой к WAN, загрузке роутера и сроку аренды, без повторной записи неизменённых данных.
- Shadow использует отдельный маршрут WAN и защиту от DNS-петли, сохраняя фильтр AdGuard, кэш, объединение одновременных запросов и DNS-обучение AWG. Остальные домены используют настроенный DoH/VPN; при недоступности DNS WAN совпавшие домены получают ошибку без скрытого перехода к публичному DNS. В панели видны источник ответа и отдельный счётчик Shadow.
- Экспорт всех сохранённых настроек DNS в JSON включает адрес и порт, состояние сервиса, пулы и bootstrap, выбор VPN, группы доменов, параметры кэша и планировщика, Shadow DNS, AdGuard, собственные правила и исключения. Несохранённая форма, рабочий кэш, счётчики, журнал и приватные VPN-ключи в экспорт не входят.
- Импорт показывает будущие адрес, порт и VPN до применения. Подключения сопоставляются по отпечатку публичных параметров; отсутствующее или неоднозначное совпадение требует выбора замены. Изменённые после просмотра настройки требуют повторной проверки; ошибка запуска возвращает прежнюю конфигурацию.
- Переключатель **«Планировщик DNS»** отключает фоновые проверки, сбор оценок и ранжирование, сохраняя обычные параллельные запросы и независимый fast-dns. Пулы с одной доступной включённой парой DoH и маршрута автоматически пропускают оценки и проверки до появления конкурента. Старые настройки и экспорты без этого поля сохраняют включённый планировщик.
- Кэш учитывает TTL ответов и кэширует NXDOMAIN/отсутствие нужного типа записи по подходящей SOA и SOA.MINIMUM. Регистр имени не создаёт отдельную запись; типы A/AAAA/HTTPS, параметры DNSSEC и EDNS разделяются. Ошибки, усечённые ответы и нулевые TTL не сохраняются.
- Одновременные одинаковые запросы используют одно общее обращение к провайдеру, с ограничением числа операций и ожидающих клиентов. Отмена одного клиента не прерывает остальных; очистка кэша не позволяет старому запросу заполнить его заново.
- Проверка домена, журнал и статистика различают **новый ответ**, **ответ из кэша** и **общий ответ**. Провайдер и VPN повторно использованного ответа показываются как первичный источник. Сохранение тех же работающих настроек или повторное включение DNS не сбрасывает кэш и счётчики.
- В журнале, последней DNS-операции и проверке домена видны фактический IP отправителя и UDP/TCP/API. Локальный DNS-посредник и проверка из панели помечаются отдельно; исходное устройство за посредником не угадывается.
- Журнал использует кольцевой буфер с пределом 128 КиБ. Панель получает только новые события по курсору; после перезапуска экземпляра журнала прежняя история не смешивается с новой.

### Маршрутизация AmneziaWG

- Общие настройки маршрутизации сохраняются независимо от выбранного VPN. Добавление или выбор подключения сохраняет открытую вкладку и редактор правил; параметры и ключи туннеля остаются у своего подключения.
- Переключатель **«Все поддомены»** расположен внутри полного редактора матчей и действует также на готовые списки. Включение учитывает домен и его поддомены, выключение делает обычные имена точными; сложные маски, регулярные выражения и IP сохраняют своё значение. Старые правила без поля сохраняют прежнюю семантику.
- Удаление VPN сохраняет связанные правила в состоянии **«Ожидает подключения»**, включая порядок, матчи, источники LAN, поддомены и резервные подключения. Для возврата в работу требуется выбрать замену; удалённые резервные подключения также можно заменить отдельно.
- Экспорт/импорт всех правил в JSON использует короткие отпечатки сервера, протокола и интерфейса. Единственное точное совпадение привязывается автоматически; другое или отсутствующее подключение требует ручной замены либо ожидания. Приватные ключи и пароли не экспортируются.
- Готовые списки включаются в экспорт как переносимые снимки без изменения исходных файлов. Импорт может добавить правила или заменить список; повтор после потерянного ответа не создаёт дубликаты, а изменение конфигурации другим клиентом требует повторной проверки.
- Опрос панели выполняется последовательно и приостанавливается на время настройки. Устаревший ответ не заменяет состояние после сохранения, чтение ограничено по времени, черновик сохраняется при неоднозначном результате записи. **«+ правило»** создаёт локальный черновик; отмена не добавляет пустое правило и не применяет маршруты.
- Кэш расширения списков и таблица DNS-правил учитывают ревизию изменений. Поддомены применяются после расширения без изменения общего списка; точные имена проверяются по таблице без отдельного регулярного выражения для каждого домена.
- DNS-обучение проверяет установку IP в маршруты **до выдачи ответа устройству**, учитывая IP-подсказки HTTPS/SVCB. Ошибка установки возвращает DNS-ошибку; подготовка DNS-данных выполняется до блокировки применения, исключая ожидание собственного DNS.
- Прогрев списков повторно использует известные IP и объединяет запросы одного имени. Неудачная попытка откладывает повтор на минуту; общий бюджет подготовки — 30 секунд, одного имени — 15 секунд. Резервный resolver запрашивает только недостающую семью адресов; TTL ответов устройствам не продлевается.
- Watchdog проверяет исправную политику без ежеминутной переустановки firewall и блокировки DNS. Обновление неизменённых ipset сохраняет изученные адреса и DNS-перехват; ошибка подготовки не очищает работающие наборы. `iptables-restore --noflush` сохраняет переходы до применения новой таблицы.
- Временная блокировка старого `iptables-restore` на Keenetic вызывает ограниченный повтор. После ошибки watchdog и восстановление VPN проверяют также ipset и DNS-перехват до подтверждения готовности. Панель показывает ход применения, ошибку и необходимость переподключить уже открытые соединения.

### Стабильность сети и статистика

- ARP Spoofing на Keenetic применяет MAC через штатный KeeneticOS/NDM, проверяя соответствие native bridge и интерфейса ядра. Исправлено расхождение MAC в Ethernet-заголовке и ARP-ответе, возникавшее при изменении только через `ip link`.
- Исходный MAC сохраняется до изменения; частично применённая настройка откатывается, выключение или исключение интерфейса возвращает его адрес. Режим AUTO выбирает проверенные LAN-мосты и исключает WAN. Периодическая проверка не переустанавливает неизменённый MAC и не рассылает gratuitous ARP без необходимости.
- Фоновая проверка firewall DNS не удерживает общий mutex маршрутов во время внешних команд. Ожидание xtables не блокирует обычное чтение доступных путей; остановка отменяет проверку, а её устаревший результат не восстанавливает остановленный hook.
- Опрос системы использует общий снимок `/proc` не чаще раза в секунду даже при нескольких клиентах. Исправлены учёт I/O wait, двойной подсчёт guest CPU и повторное использование PID. Панель поясняет: 100% CPU процесса соответствует одному ядру.

### Удалено

- Неработающая интеграция Pi-hole: сервис, контейнерный установщик, API, вкладка и альтернативная цепочка DNS. При обновлении сохраняется очистка старых перенаправлений на порт 5353; встроенный DNS Server и DNS-обучение AWG продолжают работать.

### Сборка и зависимости

- `npm test` автоматически находит и запускает регрессионные тесты интерфейса; эта проверка включена в общий скрипт сборки и CI.
- Сторонний плагин объединения UI заменён небольшим локальным сборщиком одного HTML. Он проверяет, что все локальные ресурсы встроены, и завершает сборку ошибкой при оставшихся ссылках. Удалена ненужная цепочка glob-зависимостей с уязвимой `braces` (GHSA-vfj7-8cjw-p6xm); это зависимость среды сборки, а не роутерного сервиса.

### Обновление и границы проверок

- Изменения проверены Go-тестами, тестами интерфейса, сборками Linux и нативными тестами на Keenetic ARM64. На роутере проверены перенос правил, DNS-кэш, общий ответ на одновременные запросы, Shadow DNS, проводник, разделение версий NFQWS2 и сохранение работающих VPN/настроек. ## [v1.6.0] — 2026-09-09

Добавлен **DNS Server** — единый DNS-сервис на роутере, который определяет IP-адреса
сайтов через несколько DNS-провайдеров и доступных маршрутов. Можно назначить отдельный
DNS для группы доменов, а выбор быстрого и надёжного пути доверить планировщику.
Сервис выключен по умолчанию и включается в панели.

### Добавлено

- **Несколько DNS-серверов в одном пуле.** До восьми DoH-серверов (DNS-over-HTTPS) можно добавить вручную или выбрать из готового списка. Сервис обращается к нескольким вариантам параллельно: первый корректный ответ сразу возвращается устройству, остальные попытки отменяются. Зависший провайдер не заставляет ждать, если другой уже ответил.
- **Свой DNS для нужных сайтов.** Один DoH-сервер или целый пул можно назначить домену либо группе доменов, включая поддомены. Например, использовать специальный DNS для Claude и Grok, а остальные сайты обслуживать через общий пул. Списки доменов можно вставлять по строкам или через запятую; повторы удаляются автоматически.
- **DNS через NFQWS, WARP и AWG.** Запросы могут проходить через NFQWS и VPN-туннели AmneziaWG, включая Cloudflare WARP. Режим «Авто» использует доступные AWG-подключения; также можно выбрать конкретный туннель или оставить только NFQWS. Несколько путей помогают получить ответ, когда отдельный DNS или маршрут недоступен.
- **Адаптивный планировщик маршрутов.** Для каждой пары «DNS-сервер + маршрут» учитываются задержка, успешные ответы и ошибки. Быстрые и надёжные варианты получают приоритет, а остальные регулярно перепроверяются в фоне и могут вернуться в лидеры. Отмена после ответа другого сервера не считается ошибкой. В панели видны очередь, оценки и результаты проверок — для общего пула или выбранного домена.
- **fast-dns.** IP-адреса самих DoH-серверов заранее кэшируются и обновляются раз в час, чтобы не искать их заново перед запросами. Настройка включена по умолчанию; вручную заданные IP имеют приоритет.
- **Кэш DNS с настройкой времени хранения.** Повторные запросы обслуживаются из памяти. Максимальное время хранения настраивается от 1 секунды до суток, по умолчанию — 1 час, с учётом TTL ответа провайдера. Кэш можно очистить кнопкой без перезапуска сервиса.
- **Статистика и консоль DNS.** Запросы, задержки, ошибки и использование кэша показаны в начале страницы DNS Server и отдельным блоком на Dashboard. Включаемый журнал хранит до 128 КиБ в памяти и автоматически удаляет старые записи. Отмены сгруппированы компактно, а подробности ошибок доступны для диагностики; есть пауза просмотра и очистка.
- **Порты в настройках системы.** Порты DNS Server и веб-панели можно менять из раздела «Система» с проверкой доступности. Локальный DNS работает по UDP/TCP, по умолчанию на порту `5355`; обращения к внешним DoH-серверам идут по HTTPS с проверкой сертификата.

### Исправлено

- Выключенный DNS-сервер показывает нейтральное состояние маршрута NFQWS вместо вводящей в заблуждение надписи «недоступен».
- Панель со сборкой новой версии больше не предлагает старый релиз как обновление; переход с предварительной сборки на стабильную версию того же номера сохранён.

- **AWG2: SNI-маршрутизация — маршрутизация по имени сайта из TLS-рукопожатия** (тумблер «SNI-маршрутизация (CDN + DoH)» во вкладке «Маршрутизация»). Пассивный сниффер (AF_PACKET на LAN-мостах, без внешних зависимостей) читает имя сайта (SNI) прямо из ClientHello — это **не зависит от DNS** устройства (работает при DoH/DoT) и от плавающих/общих IP за CDN (Cloudflare, Akamai и т.п.): совпавший с зоной «Включить» домен заводится в туннель по тому IP, к которому **реально подключилось устройство**, на ~1 час (набор `awg2_sni` с таймаутом). Только чтение — соединение никогда не рвётся; первый коннект к новому адресу ещё идёт напрямую (по нему и учимся), дальше — через VPN. Парсер SNI переиспользован из `tlsblob`. Дополняет маршрутизацию по доменам (DNS) и по IP/CIDR.
### Исправлено
- **AWG2: «звёздочка `*` = весь трафик через VPN».** Раньше `*` (и `*.com`, `*.net`) в зоне «Включить» не заводили в туннель ничего, кроме доменов, которые резолвятся в конкретный IP (например `2ip.ru`), — поэтому «работало только на 2ip». Теперь `*` отдельной строкой во «Включить»-зоне означает «весь трафик» и применяется на уровне файрвола (помечается всё, кроме локальной сети, приватных адресов и самого VPN-сервера) — это надёжно и **не зависит от DNS** (работает и для сайтов с уже закэшированным DNS, и при DoH/DoT). Вместе с «Исключить»-зоной = всё через VPN, кроме неё.
- **AWG2: маски доменов (`*.com`, `*ip*`, `[re]…`) теперь работают, даже если тумблер «перехват DNS» выключен.** Раньше в режиме по умолчанию маски молча игнорировались (их нельзя зарезолвить как обычный домен), и в туннель попадали только «плоские» домены. Теперь любая маска в активной зоне автоматически включает DNS-перехват, который их и обрабатывает.
- **AWG2: «плоские» домены в режиме «по зонам» перестали устаревать.** Фоновое пере-резолвинг доменов раз в ~15 мин не срабатывало для зональной конфигурации (проверялся старый общий режим) — со временем IP доменов «протухали». Теперь пере-резолвинг идёт по фактическому направлению зон.
- **AWG2: «Переразвернуть сервер» больше не ломает существующий туннель.** Повторное развёртывание уже развёрнутого сервера перегенерировало ключи и обфускацию и обнуляло публичный ключ пира — туннель падал. Теперь у развёрнутого сервера ключи/обфускация не трогаются, а пустой публичный ключ пира восстанавливается из приватного.

## [v0.12.0] — 2026-05-31
### Добавлено
- **AWG2: маршрутизация по доменам с поддоменами и масками** (тумблер «Маски и поддомены доменов (перехват DNS)» во вкладке «Маршрутизация»). Панель поднимает прозрачный DNS-перехватчик: DNS-трафик локальной сети (:53) заворачивается на встроенный прокси (iptables REDIRECT для всех LAN-мостов), который форвардит запросы штатному резолверу Keenetic (`ndnproxy`) и при совпадении имени с зоной заводит его IP в туннель (ipset). Форматы записи в зоне:
  - `domain.com` — домен **и все его поддомены** (`a.domain.com`, `x.y.domain.com`);
  - маски `*main.com`, `server*`, `test##.com` (`*` — любая последовательность символов, `#` — ровно один);
  - регулярные выражения `[re]^.*\.cdn\.net$`.
  Так в туннель заводятся целые сервисы с миллионами поддоменов, не перечисляя их вручную. Перехват действует только пока маршрутизация активна и снимается вместе с ней; обычный DNS не ломается (прокси резолвит все имена, в туннель попадают только совпавшие). Ограничение: устройство, использующее шифрованный DNS (DoH/DoT) напрямую, обходит перехват — там запросы роутеру не видны.

## [v0.9.3] — 2026-05-30
### Добавлено
- **Кнопка «Перезапуск» на Дашборде** — выбор сервисов (NFQWS2 / TG WS Proxy) и
  их перезапуск прямо из веб‑интерфейса, без захода по SSH. Для **NFQWS2**
  выполняется надёжное восстановление (стоп → `killall nfqws2` → старт), которое

### Диагностика
- **Найдена причина «после ребута nfqws2 не стартует».** Апстримный init
  `S51nfqws2` в `is_running()` ищет процесс через `pgrep -nf /opt/usr/bin/nfqws2`,
  а эта строка — **подстрока** нашего `/opt/usr/bin/nfqws2-strategy` (и `-n`
  выбирает именно наш, как более новый). Init принимает наш процесс за nfqws2,
  считает сервис «не запущенным», при stop не убивает настоящий nfqws2 — тот
  остаётся «осиротевшим» и держит очередь 300, поэтому свежий старт не может её
  занять. Кнопка «Перезапуск» выполняет корректное восстановление (`killall
  nfqws2` ищет по точному имени процесса и наш `nfqws2-strategy` не трогает).
  Постоянное исправление (переименование бинаря, чтобы не матчился) — отдельно.

## [v0.4.1] — 2026-05-28
### Исправлено
- **Обновление/перезапуск нашего сервиса больше не ломает основной nfqws2.**
  Раньше при остановке активный прогон убивался вместе с процессом, а его
  временные правила iptables (песочницы `STRAT_*`) оставались — в частности
  правило `CONNMARK 0x20000000`, помечающее соединение как исключённое из
  основного nfqws2. После рестарта соединения, чей исходящий порт попадал в
  «утёкший» диапазон, переставали обходиться DPI — выглядело как «nfqws2 упал».
  Теперь сервис при остановке (SIGTERM) отменяет активный прогон/проверку и
  гарантированно сносит все свои песочницы (`STRAT_*`) и оставшиеся тестовые
  процессы nfqws2 (по метке `--writeable=/tmp/nfqws2-strategy/`), а **при запуске
  подчищает утёкшее с прошлого раза — то есть уже сломанная установка чинится
  сама при первом старте новой версии.** Основной nfqws2 (очередь 300) при этом
  не затрагивается. Init-скрипт при `stop` дожидается завершения процесса и
  делает `kill -9` как запасной вариант (для новых установок).

## [v0.4.0] — 2026-05-28

  протокол, состояние, источник (LAN), назначение, порт, трафик, зона. Фильтр
  (IP/порт/протокол/состояние), сортировка по колонкам, переключатель «только
  проблемные» и пагинация.

  LAN (IP + MAC + мост br0/br2). Для каждого устройства видно, что работает и

  без сторонних утилит; счётчики байт под аппаратным offload ([FASTNAT]) могут
  отставать, поэтому используются только для отображения, а определение
  «не отвечает» опирается на состояние и флаги (они корректны всегда).

## [v0.3.0] — 2026-05-28
### Добавлено
- **Вкладка «DNS»** — список шифрованных DNS-серверов (DoH/DoT) с добавлением,
  удалением и сбросом к стандартным. По умолчанию засеяны провайдеры Google,

  к этому IP, а SNI/Host остаётся исходным хостом — так видно, какой DNS вместе
  с какой стратегией реально открывает доступ.

## [v0.2.0] — 2026-05-28
