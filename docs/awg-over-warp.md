# Аварийное подключение AmneziaWG через WARP

Дата проверки: 27 октября 2026 года. Статус: исследование и проект реализации;
автоматический вложенный туннель пока не реализован.

## Возможность и ограничения

Подключение `роутер → WARP → AWG-сервер → Интернет` технически возможно.
WARP должен переносить UDP-пакеты подключения AWG к его обычному адресу и порту.
Трафик устройств продолжает выходить через выбранный AWG-сервер. Добавление
самого WARP последним резервным подключением даёт другой результат: выход через
Cloudflare, без подключения к выбранному AWG-серверу.

Cloudflare описывает перенос IP-трафика через WARP на WireGuard или MASQUE в
[документации архитектуры клиента](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/configure/route-traffic/client-architecture/).
Это подтверждает транспортную возможность. Работа конкретного AWG-сервера через
Cloudflare требует отдельной проверки; официальной гарантии такого обхода нет.

| Состояние | Ожидаемый результат |
| --- | --- |
| IP или UDP AWG-сервера недоступен из сети провайдера, сервер работает и доступен из Cloudflare | Вложенный туннель может восстановить доступ |
| AWG-процесс остановлен, VPS выключен, ключи неверны либо firewall сервера блокирует Cloudflare | WARP не устраняет неисправность |
| WARP недоступен из сети провайдера | Аварийный путь тоже недоступен |
| WARP работает, но Cloudflare не пропускает соединение к нужному серверу | Нужен другой сервер или другой транспорт |

По таймауту AWG-сервера нельзя установить причину неисправности.
Для этого нужны проверка из независимой сети и новый AWG-handshake
через WARP. ICMP/ping или доступность SSH отдельно не подтверждают работу AWG.

В проекте WARP создаётся как импортированный WireGuard-профиль и работает через
установленный движок AmneziaWG. Это не установка официального приложения WARP
с MASQUE: его возможности, включая переключение на TCP, автоматически не
появляются. Cloudflare публикует разные ingress-адреса и порты для WireGuard и
MASQUE в [требованиях к firewall](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/firewall/).

## Почему изменения одного маршрута недостаточно

Сейчас `client_linux.go` при запуске, а `multi_policy_linux.go` при применении
политики закрепляют endpoint каждого туннеля за WAN. Восстановление legacy full
также устанавливает WAN-маршрут. Самостоятельная замена `/32` маршрута до
AWG-сервера на WARP будет перезаписана этими механизмами. Глобальная замена ещё
и меняет путь всех соединений роутера к этому адресу.

Нужно разделить два уровня маршрутизации:

1. Трафик устройств и DNS идёт во внутренний интерфейс AWG по существующим
   правилам и с существующим killswitch.
2. Только зашифрованный UDP-транспорт этого интерфейса идёт через внешний
   интерфейс WARP. Собственный endpoint WARP остаётся на WAN.

Предпочтительный механизм — отдельная метка UDP-сокета внутреннего AWG через
UAPI `fwmark` и выделенная таблица маршрутизации. Закреплённый в проекте движок
[amneziawg-go v3.1.20260828](https://github.com/amnezia-vpn/amneziawg-go/blob/v3.1.20260828/device/uapi.go)
поддерживает `fwmark` и применяет его к транспортному сокету. Текущий
`awg.RenderUAPISet` эту настройку не отправляет.

Выделенная таблица должна направлять только помеченные пакеты к endpoint
AWG-сервера через WARP и запрещать им переход к WAN при потере WARP. Выбор
свободной метки, маски, таблицы и приоритета должен учитывать действующие правила
Keenetic/OpenWrt, NFQWS и существующие туннели. Присваивать произвольную метку
без проверки нельзя: здесь уже используются верхние биты для маршрутизации,
NFQWS и диагностических сокетов. Цепочки OUTPUT должны сохранять метку
транспорта. WAN-подсказки endpoint могут оставаться для прямого режима, поскольку
отдельное policy rule выбирает таблицу вложенного транспорта раньше main.

Дополнительный UDP-relay на loopback возможен как альтернатива, но потребует
своего жизненного цикла, восстановления после рестарта панели и той же отдельной
маршрутизации сокета. Одного `SO_BINDTODEVICE` недостаточно, если более точный
маршрут в используемой таблице указывает на WAN.

## Предлагаемое поведение

У основного подключения нужен отдельный выбор **«Аварийный транспорт через
WARP»**, который хранит ID внешнего WARP-подключения. Выбор WARP обычным резервом
должен оставаться отдельной операцией.

После исчерпания прямых резервов supervisor поднимает WARP, подтверждает его
handshake и передачу данных, устанавливает таблицу транспорта, затем
переподключает тот же внутренний AWG через WARP. Рабочим результатом считаются
свежий handshake именно внутреннего AWG и успешный запрос через него.
В панели отображаются оба уровня и отдельные причины ошибки.

Вложение не должно создавать второй одновременно работающий экземпляр того же
AWG-пира. WireGuard запоминает последний аутентифицированный endpoint — это
описано в [механизме roaming](https://www.wireguard.com/#built-in-roaming).
Два экземпляра с одним ключом способны переключать endpoint друг у друга.
Возвращение с WARP на WAN требует переключения транспорта существующего
интерфейса. Для независимой параллельной пробы прямого пути нужен отдельный
диагностический пир на сервере либо краткая контролируемая смена транспорта;
сам по себе ping не доказывает восстановление прямого AWG.

Зависимости должны быть ацикличны. WARP нельзя вкладывать в собственный дочерний
AWG или выключать, пока его использует другой аварийный путь. Ручное выключение,
удаление подключения, обновление движка и перезапуск панели должны приводить
к согласованному состоянию обоих уровней и удалению только собственных правил.

MTU внутреннего AWG должен учитывать эффективный MTU WARP, UDP/IP, заголовки AWG
и максимальные дополнения конкретного профиля. Универсальное значение 1280 не
решает эту задачу для всех параметров обфускации. Нужны ограничение внутреннего
MTU, согласованный TCP MSS и проверка больших UDP-пакетов; наличие handshake
при этом не гарантирует прохождение больших пакетов. Низкая скорость возможна,
но её величину определят маршрут, потери и нагрузка CPU роутера.

## Проверка перед включением автоматического режима

Нужен стенд с реальным Keenetic/OpenWrt и доступом к AWG-серверу. Приёмочные
сценарии: блокировка только прямого UDP, отказ всех прямых резервов, отказ WARP,
реальная остановка AWG-сервера, восстановление WAN, общая зависимость двух
подключений от WARP, выключение пользователем, рестарт панели и пересборка
firewall прошивкой. Отдельно проверяются DNS, новые HTTPS-соединения, длинная
загрузка, крупные UDP-пакеты и отсутствие отправки вложенного транспорта на WAN
после потери WARP.

Результат должен показывать время переключения, handshake каждого уровня,
фактический выход через AWG, выбранный MTU и причину неуспеха. До такой проверки
в панели не следует обещать «подключение в любом случае» или обозначать обычный
WARP-резерв как вложенный туннель.
